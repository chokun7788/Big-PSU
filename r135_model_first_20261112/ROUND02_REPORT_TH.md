# รอบ 02 — บริบทของราคาและสัญญารวมคำตอบ

ทำใน candidate model-first แยก วันที่ 12 พฤศจิกายน 2026 ไม่แทน Flow หลัก ไม่แตะ protected model หรือฐานข้อมูล owner/live/frozen

## ผลที่ใช้ได้จริงในรอบนี้

คำถาม **“นักศึกษา PSU เล่น PC 30 นาที เสียกี่บาท แล้วจองยังไง”** ผ่านหน้าแชตรุ่นทดลอง 8145 จริง โมเดลเสนอ `[["P",0,6],["B",7,7]]` คือเก็บชื่อกลุ่มผู้ใช้ บริการ และระยะเวลาไว้ในงานราคา แยกจากงานจอง

คำตอบแสดง PC สองบริการตามต้นทาง แห่งละ **0 บาทสำหรับ 30 นาที** พร้อมเงื่อนไขวันเริ่ม–สิ้นสุดที่ยังไม่ยืนยัน และขั้นตอนจอง ไม่มีข้อความ “ส่วนที่ยังไม่มีแผน...” หรือ “ยังยืนยันการใช้...30 นาทีไม่ได้” ซึ่งขัดกับสิ่งที่ตอบแล้ว ใช้เวลา **16.49 วินาที** มี actual model provenance และ typed contracts ของสองงานใน log

นี่เป็นการยืนยันหนึ่งกรณี ไม่ใช่การรับรองว่าระบบแก้บริบทหรือความหมายได้ทั้งหมด ขั้นตอนจองที่แสดงเป็นขั้นตอนทั่วไปที่ต้นทางบันทึก ยังไม่พิสูจน์ workflow เฉพาะกรณีราคา 0 บาทหรือการทำธุรกรรมจริง

## สาเหตุและการแก้

1. **บริบทหาย:** ก่อนแก้ โมเดลเคยเลือกเฉพาะ “เสียกี่บาท” จึงไม่มี PSU, PC และ 30 นาทีให้ reader ตรวจ ไม่ใช้การแนบคำถามทั้งหมดเข้าแต่ละงานเป็นทางแก้ เพราะอาจข้ามบริการหรือเงื่อนไขของอีกงาน
2. ทดลอง protocol 5 ช่อง แยก predicate range กับ context range ตรวจ literal containment และไม่ให้ context ครอบ predicate อีกงาน ได้ผล source-only แต่โมเดลจริงเลือก index ผิด จึงถอนรูปแบบ 5 ช่องจาก schema ที่ขอให้โมเดลสร้าง เก็บ parser ไว้สำหรับ replay ที่ระบุแผนเอง ไม่เปิดเป็น default generation
3. กลับใช้แผนกระชับ 3 ช่อง โดยให้โมเดลเลือกข้อความทั้งส่วนที่รวมบริบทของงานนั้น ไม่มีการขยาย span หลังโมเดลอย่างเงียบ ๆ ถ้าโมเดลยังทิ้งบริบท ระบบยังถามบริการหรือแจ้งเงื่อนไขที่ใช้ไม่ได้ตามจริง
4. **ข้อความขาดแผนซ้ำ:** ตัวรวมคำตอบเดิมทิ้ง execution contracts ของลูก ทำให้ verifier เห็นคำตอบที่ตรวจแล้วเป็นงานไม่ถูกวางแผน รอบนี้ประกอบ parent contract ด้วย raw offsets, task IDs, claims, source receipts และ calculation receipts จากแต่ละลูก
5. พบอีกจุดว่า code B หมายถึงวิธีจอง แต่ canonical operation ถูกเก็บเป็น owner_policy กว้าง ๆ แก้การประกาศเป็น `policy.booking_steps` ทั้ง parent และ child ไม่ลดเกณฑ์ matches ของ verifier
6. ตัวตรวจท้ายยังทำงานเหมือนเดิม ไม่ลบ notice ด้วย regex ไม่ปิด independent observer และไม่เพิ่มงานที่โมเดลตกหล่นแทนโมเดลอย่างเงียบ ๆ

แผน 3 ช่องไม่ได้แยก predicate span ต่างหาก จึงบันทึก `predicate_span_separately_proposed=false` ไม่อ้างว่ารู้ขอบเขต predicate อย่างแม่นยำ การเลือกบริบทโดยโมเดลยังไม่ใช่ semantic proof

## หลักฐานและผลตรวจ

| ชุดตรวจ | ผล | ความหมาย |
|---|---|---|
| source/contract supplied-plan ก่อนแก้ canonical B | 20/21 ผ่าน | ยังแจ้งขาดแผนจองทั้งที่ตอบแล้ว เก็บ failure ไว้ |
| source/contract หลังแก้ | 21/21 ผ่าน | รวมราคา+จอง, exact raw spans, duration proof, ลบงานจองแล้วยังตรวจเจอ, ถอน proof แล้วยังไม่รับ duration, บริการไม่รู้จักไม่ให้ราคา 0, ข้าม predicate ถูกปฏิเสธ |
| protocol/source regression | 12/12 ผ่าน | schema/range/timeout/no silent fallback/wrong edition/ราคา 0 ปกติ ใช้ mock ไม่ใช่ความสามารถโมเดล |
| โมเดลจริง protocol 5 ช่อง | 1/4 กรณีผ่าน | ราคาได้ แต่ static/live ผิดช่วง; typo เหลือหนึ่งงาน จึงถอนจาก default |
| โมเดลจริง protocol กระชับพร้อมบริบท | 2/4 กรณีผ่าน | live และราคา+จองผ่าน; static เลือก controls ผิด; typo ตกรายการจอง |
| HTTP price+booking รุ่น trial02 | 1 request, 9 checks ผ่าน | อ่านคำตอบและ persisted trace ของ request เดียวกัน ยืนยันการเชื่อมต่อจริง |

สองชุดโมเดลเป็น development cases เดิมที่ใช้ช่วยออกแบบ prompt ไม่ใช่ unseen test ไม่เอา 2/4 ไปเรียกคะแนนความแม่นยำทั่วไป และไม่เอา source/mock checks ไปรวมกับ inference เป็นคะแนนเดียว

รอบ HTTP ครั้งแรกอ่าน transcript เร็วกว่าการเขียน log แบบ asynchronous ทำให้ 3 trace checks ล้ม ทั้งที่ business answer ถูก เก็บ RESULT.json เดิมไว้ แล้วอ่าน trace ของ **request เดิม** หลังบันทึกเสร็จ ได้ PERSISTED_CHECKS.json ผ่านทั้ง 9 ข้อ ไม่มีการส่งคำถามซ้ำเพื่อแก้ผล ต่อมาปรับ harness ให้รอเฉพาะ persisted row สูงสุด 5 วินาที ไม่ได้รัน HTTP เพิ่มจากการแก้ harness

## ข้อผิดที่ยังเปิด

- โมเดลตี “มีให้เล่นบนเครื่องอะไรบ้าง” เป็นปุ่มควบคุมเกมในชุดล่าสุด ทำให้ระงับคำตอบบริการที่จริงมีข้อมูล ถือเป็น regression ของ prompt ทดลอง ยังไม่พร้อมเปิดใช้เป็นเส้นทางหลัก
- คำผิด “มีเกสอะไรบ้าง แล้วจองยังงไ” เลือกงานรายชื่อเกมครอบทั้งข้อความแล้วตกงานจอง ตัวตรวจอิสระยังแจ้งงานจองที่หาย ซึ่งเป็น notice ที่ควรคงไว้
- ยังมีความกำกวม “พร้อมเล่น” และขอบเขตร่วมระหว่างหลายบริการ/หลาย audience ที่ยังไม่ผ่าน actual model acceptance
- generic procedure support ไม่เท่ากับการยืนยัน workflow ฟรีหรือสถานะจองจริง
- source currentness/authority, owner editor HTTP lifecycle, attachment coverage, cooldown/deadline และทั้ง 48/76 requirements ยังไม่ปิดจากรอบนี้

## ขั้นถัดไป

พักการปรับ prompt/context format แบบเดิมหลังผลยังไม่ครบสองแนวทาง ไม่วนชุด 4 ข้อเดิมโดยไม่มีการเปลี่ยนสาเหตุร่วม เก็บ contract fix ที่ตรวจแล้วใน candidate ทดลอง และยังไม่ promote ไปแทน parent

งานถัดไปคือ audit ตัวตีโจทย์ที่มีอยู่และ schema ที่โมเดลเคยฝึก เพื่อเลือกแนวทางอื่นในการแยก static offering/controls และรักษางานรอง ไม่เพิ่มกฎแก้ประเภทผิดเงียบ ๆ หรือย้ายคำตอบเก่าเป็น gold ใช้หลักฐานผิดจริงกำหนด positive/negative แล้วจึงทดสอบ integration ใหม่แบบทีละคำถาม ไม่รัน 200/2111 ในรอบนี้
