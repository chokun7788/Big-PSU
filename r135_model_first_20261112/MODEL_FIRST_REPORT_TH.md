# ผลทดลองให้โมเดลตีโจทย์ก่อน — 12 พฤศจิกายน 2026

## ข้อสรุป

ทำต้นแบบแยกแล้ว โมเดลจริงอ่านคำถามเต็มและเสนอหลายงานได้ ก่อนส่งเข้า reader และ verifier เดิม ยังไม่พร้อมแทน Flow หลัก เพราะพบการเลือกเจตนาผิดและบริบทของงานหาย ไม่ได้พิสูจน์ว่าแม่นกว่าเดิมทั้งระบบ

รุ่นเดิม `r135_recovery_loop_20261112` และข้อมูล owner/live/frozen เก็บไว้ โมเดลบน 12921 ไม่ได้หยุด เปลี่ยนน้ำหนัก หรือติดตั้งใหม่ รุ่นทดลองใช้แชต 8145 และฐานข้อมูลสำเนาของตนเอง

## สิ่งที่ทำจริง

1. ส่งคำถามเต็มเข้า local model หนึ่งครั้ง ไม่ใช้ตัวแบ่งประโยคตามคำเชื่อมเดิมก่อนเรียกโมเดล
2. ให้โมเดลเสนอรหัสงานและช่วงข้อความต้นฉบับแบบกระชับ เช่น zone และ services เพื่อประหยัด token และตรวจรูปแบบได้
3. ตรวจ JSON จำนวนงาน รหัส และช่วงข้อความ ไม่ยอมให้แผนแทรกตัวเลขหรือ fact เพิ่มเอง
4. ส่งแต่ละงานเข้า reader ตามประเภทที่โมเดลเสนอ โดยไม่ให้ native planner แก้ประเภทผิดของโมเดลอย่างเงียบ ๆ
5. ใช้ finish_plan เตรียมความสัมพันธ์และ applicability receipts แล้วผ่าน obligation verifier เดิม การขาดขั้นตอนนี้ในต้นแบบแรกทำให้บริการและขั้นตอนจองถูกระงับ เก็บผลก่อนแก้ไว้ครบ
6. แยกข้อมูลว่าเกมมีบนบริการใดออกจากสถานะว่าเครื่องว่างตอนนี้ ไม่มีการเดาข้อมูลว่างสด
7. เก็บแผนดิบ provenance คำตอบ claims receipts และผลที่ล้มสำหรับวิเคราะห์

ยังใช้ renderer ข้อมูลที่ตรวจแล้ว ไม่ได้เปิดให้โมเดลเขียนคำตอบอิสระ และ catalogue ของต้นแบบยังไม่ครอบคลุม 14 หมวดทั้งหมด

## ผลจากโมเดลจริง

การลอง protocol JSON ยาวครั้งแรกเกิด client timeout และ backend ส่ง JSON ที่ยังไม่สมบูรณ์ภายหลัง จึงเก็บเป็น failure ไม่คิดว่าตีโจทย์สำเร็จ เปลี่ยนเป็นแผนกระชับและเว้นเวลาระหว่าง server generation กับ socket deadline โดยไม่แก้ protected server

ชุดพัฒนา 4 ข้อครั้งแรกผ่านเงื่อนไขเฉพาะกรณี 2/4 แต่ native executor เดิมแก้ประเภทงานผิดบางกรณี ทำให้คำตอบดูถูกทั้งที่โมเดลผิด จึงเปลี่ยน adapter ให้เห็นข้อผิดของโมเดลจริง

ชุด 4 ข้อถัดมาผ่าน 1/4 ก่อนแก้ adapter เตรียมหลักฐาน พบทั้งข้อผิดโมเดลและข้อผิดการเชื่อมต่อ ไม่ใช่คะแนน semantic accuracy หรือผลของโค้ดสุดท้าย หลังแก้ adapter ใช้แผนที่บันทึกเดิม replay ทั้ง 4 ข้อโดยไม่เรียกโมเดลซ้ำ: บริการ Tekken และขั้นตอนจองกลับมาตอบได้ แต่ข้อผิดตีโจทย์และบริบทหายยังคงอยู่

การเรียกโมเดลจริงหลังแก้ adapter ด้วยคำถามผู้ใช้:

> Tekken 8 อยู่โซนไหน แล้วเครื่องไหนพร้อมให้เล่น Tekken 8 บ้าง

ใช้ 16.77 วินาที โมเดลเสนอ zone + studio_services และตอบได้ทั้ง:

- PC Zone; PlayStation 5 Zone
- PC #01-#02; PlayStation 5 #01-#02
- กำกับว่าเป็นบริการที่มีเกม ไม่ใช่ยืนยันว่าเครื่องว่างตอนนี้

ข้อจำกัดสำคัญ: แม้ prompt ขอให้ถามกลับเมื่อ “พร้อมเล่น” กำกวม โมเดลยังเลือก services จึงยังไม่นับว่าจัดการความกำกวมข้อนี้ผ่าน เพียงข้อมูลที่ส่งมีคำจำกัดขอบเขตกำกับไว้

provenance ของ stage ใหม่นี้เป็น **base profile ไม่มี adapter active** แม้ชื่อ model จะเป็น psu-r129:latest ไม่อ้างว่าเป็นผล planner LoRA retained

## ผลตรวจที่ไม่ใช่ inference ใหม่

- protocol/source controls 12/12 ผ่านบน adapter สุดท้าย ใช้ mocked gateway และปิด HTTP ไม่ใช่ผลความสามารถโมเดล
- replay แผนจากการเรียกจริง 4 ข้อบนโค้ดหลังแก้ แยกจาก inference ใหม่ ไม่ใช้ผล replay อ้างว่าโมเดลดีขึ้น
- actual HTTP delivery และ hash preservation บันทึกใน IMPLEMENTATION_MANIFEST.json หลังตรวจ ไม่รวมเป็นคะแนนชุดใหญ่

## ปัญหาที่ยังเปิดและขั้นต่อไป

| ปัญหา | หลักฐานจริง | งานแก้ถัดไป |
|---|---|---|
| โมเดลเลือกประเภทผิด | typo รายชื่อเกมถูกเลือกเป็นปุ่มควบคุม; รุ่น prompt ก่อนหน้าราคาถูกเลือกเป็นโซน | สร้างชุดตรวจความหมายและตัวอย่างนอก eval holdout; ไม่ให้ native correction กลบข้อผิด |
| ขอบเขตบริบทหาย | งานราคาเลือกเฉพาะ “เสียกี่บาท” ทิ้ง PSU, PC และ 30 นาที | แยก predicate span กับ context/entity/quantity spans ที่ย้อนกลับ raw ได้; ห้ามแนบคำถามทั้งหมดแทนเมื่อมีหลายบริการ |
| คำว่า “พร้อม” ยังตีความเป็น static | actual probe หลังแก้ยังเลือก S แทน R | ให้การตัดสิน ambiguity เป็นส่วนที่ตรวจรับแยก ไม่ถือ disclaimer ว่าโมเดลเข้าใจแล้ว |
| ตัวตรวจ request เดิมกับแผนใหม่ไม่ตรง | partial มีข้อความ “ส่วนที่ยังไม่มีแผน...” ซ้ำกับส่วนที่ตอบแล้ว | ปรับ contract ให้ independent observer เทียบ model tasks ได้ โดยไม่ลบ notice หรือปิด verifier เหมารวม |
| การแสดงสถานะบางส่วน | reader บางงานมีข้อจำกัด authority/currentness | ตรวจ terminal state กับข้อความที่ส่ง แยก source support จาก semantic completeness |
| coverage จำกัด | รหัสต้นแบบมี 11 แบบ; ไม่ครบ list/count/compare และ 14 หมวด | ทยอยเปิด operation เมื่อ adapter และ positive/negative ผ่าน |

ลำดับถัดไปคือผูก context ให้แต่ละงาน → จัด contract/notice → ตรวจ typo และ ambiguity ด้วยโมเดลจริงชุดเล็ก → ค่อยพิจารณาการเรียบเรียงด้วยโมเดลและชุดทดสอบรวม ไม่ฝึกน้ำหนักจาก eval holdout ไม่รัน 200/2111 ซ้ำเพียงเพื่อจุดนี้ และไม่ติดตั้งแทนตัวใช้งานจริง

ไม่มีการรับรองครบ 48/76 requirements จากต้นแบบนี้ ผลทดสอบใช้สำหรับพัฒนากลุ่มสาเหตุ ไม่ใช่ตัวประมาณความแม่นยำทั่วไป
