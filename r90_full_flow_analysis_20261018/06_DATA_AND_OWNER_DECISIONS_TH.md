## 2. ปัญหา “ข้อมูลมี แต่ยังตอบไม่ได้” ทำเองได้อย่างไร

| ชั้น | ตัวอย่างจากผลจริง | งานที่ทำเองได้ | สิ่งที่ห้ามสรุปแทน |
|---|---|---|---|
| Task recovery | Zelda: `คือกมอะๆร` | ใช้ตัวกู้ task cue พร้อมป้องกันชื่อ/ตัวเลข/ปฏิเสธ | มีชื่อเกมแล้วแปลว่าเข้าใจทั้งคำถาม |
| Field choice | Friday maintenance เลือก question | ทำ task=policy → answer contract และจำกัด field เกินโจทย์ | schema ผ่านแปลว่าเลือกคำตอบถูก |
| Relation projection | ถาม zone ได้ service names | ใช้ FK/source listing ที่ยืนยันแล้ว เลือกระดับคำตอบ | เห็นชื่อคล้ายกันจึงสร้าง relation ใหม่ |
| Short follow-up | PC → อุปกรณ์ | อ่าน delivered state + pending task แล้วผูก equipment projection | ต้องขอเจ้าของทำ FAQ แยกทุกคำตอบสั้น |
| Compound | ราคา + วิธีจอง | เก็บสถานะต่อ need; ตอบส่วนที่ยืนยันและถามเฉพาะส่วนขาด | ต้องทิ้งทั้งคำตอบเพราะ clause เดียวไม่ชัด |
| English | field labels/wording | แปลจากต้นฉบับที่ยืนยัน ตรวจเลข/เงื่อนไข/negation ให้ตรง | แปลเองแล้วบันทึก owner-reviewed |
| Scoring | literal fail เพราะสำนวน | ตรวจ semantic propositions/source ควบคู่เกณฑ์เดิม | เปลี่ยนเกณฑ์ให้ผ่านแล้วอ้างว่าระบบเก่งขึ้น |
| Diagnostics | safe response ซ่อน rejected candidate | เก็บ phase/needs/guard/latency/decision ให้ค้นย้อน | final validation ผ่านแปลว่าคำตอบร่างถูก |

ทั้งหมดเป็นแนวแก้จากงานวิเคราะห์นี้ ยังไม่ได้แก้โค้ดหรือแปลค่าในฐานระหว่างสร้างเอกสาร

## 3. ราคาและราคาเหมา: ข้อมูลมีระดับไหนแล้ว

### 3.1 ราคาใช้บริการ

มี `rate` 24 รายการ โดย 18 รายการมีช่วงมีผลที่บันทึกถึงก่อน 1 เมษายน 2026 และ 6 รายการ validity ยัง unknown การรัน R88 ใช้นาฬิกาอ้างอิงกลางเดือนตุลาคม จึงไม่ควรนำอัตราที่หมดอายุมายืนยันว่าเป็นราคาปัจจุบัน

ทำเองได้ก่อนถามเจ้าของ:

1. ไล่ตาราง/ประกาศต้นฉบับที่มีในชุดข้อมูลและรุ่นที่ใหม่กว่า ถ้ามีหลักฐานต่ออายุหรือราคาใหม่ให้ map แยกรุ่น
2. ตรวจ service_id, audience_id, หน่วยราคา, billing duration และเงื่อนไข ไม่เอาเวลาที่กันช่องจองมาคำนวณราคาเอง
3. แยกตอบ “อัตราที่บันทึกในช่วงวันที่...” กับ “ราคาปัจจุบัน” ให้ชัด
4. หากไม่มี source ต่ออายุจริงจึงส่งคำถามด้านล่าง ไม่เติมวันมีผลตามวันย้ายข้อมูล

คำถามที่ต้องถามเมื่อ source ยังไม่มี:

> ตารางค่าบริการที่ระบุสิ้นสุดวันที่ 31 มีนาคม 2026 ยังใช้อัตราเดิมหลังวันที่ 1 เมษายน 2026 หรือไม่? ถ้าใช้ต่อ ขอวันเริ่ม–สิ้นสุด/เงื่อนไขการใช้ต่อที่ยืนยันได้ ถ้าเปลี่ยน ขอรายการอัตราใหม่แยกบริการ กลุ่มผู้ใช้ และระยะเวลา พร้อมประกาศอ้างอิง

### 3.2 ราคาเหมา

มี `rental_package` 24 รายการแล้ว ไม่ใช่ยังไม่มีราคาเหมาเลย แต่ validity ของกลุ่มนี้ยัง unknown การมีจำนวนเงินครบใน preview ไม่ใช่การผ่านเงื่อนไข publication ของราคา

ต้องไล่จากเอกสารราคาเหมาที่ผู้ใช้ให้มาก่อน ไม่ขอให้กรอกใหม่ถ้าเอกสารตอบไว้แล้ว คำถามต่อไปนี้เป็น **conditional blockers** เฉพาะสิ่งที่ source ไม่ระบุ:

> ราคาเหมาครึ่งวัน/เต็มวันในเอกสารนี้เริ่มมีผลเมื่อใด และสิ้นสุดเมื่อใดหรือใช้จนมีประกาศเปลี่ยนอย่างไร?

> ครึ่งวันและเต็มวันของแต่ละแพ็กเกจหมายถึงช่วงเวลาใดหรือจำนวนชั่วโมงเท่าใด? ช่วงพักเที่ยง/บำรุงรักษานับอยู่ในช่วงใช้บริการหรือไม่?

หากไม่มี source ว่าเหมารายชั่วโมง/หลายวัน/มัดจำ/คืนเงินได้อย่างไร ให้ตอบ “ยังไม่มีข้อมูลยืนยันเงื่อนไขนี้” ไม่กระจายคำถามทั้งหมดให้เจ้าของหากผู้ใช้ยังไม่ได้ถามและไม่เป็น field ที่ต้องมีเพื่อเผยแพร่

## 4. ตารางเวลา: สิ่งที่ยืนยันแล้วกับสิ่งที่ยังคนละความหมาย

### ไม่ต้องขอผู้ใช้ยืนยันซ้ำ

- 12:00–13:00 ไม่มีช่องให้จอง
- VR 30 นาทีใช้ occupancy ของชั่วโมงเต็ม เช่น 09:00–09:30 กันช่อง 09:00–10:00
- ผู้ใช้ตรวจสถานะจริงแล้วว่าถูกต้อง คงเป็นการยืนยันจากผู้ใช้ แยกจาก corpus ที่ตั้ง live เป็น controlled_unavailable

### ทำเองได้จากต้นทางเดิม

1. เทียบ dashboard schedule กับ chat calendar โดยแยก open/service/bookable/maintenance ไม่ใช้ key `open` ทุกที่เป็นนโยบายเดียวกันโดยอัตโนมัติ
2. ใช้คำยืนยันเดิมของผู้ใช้ผูกกับ **bookable** และ **occupancy** ใน source provenance อย่างถูกประเภท
3. ตรวจ weekday, Asia/Bangkok, วันที่ปิดพิเศษ และ zone-specific exceptions ไม่ให้โซนเดียวทำให้ทั้งศูนย์ปิด
4. สถานะ “เปิดวันนี้” เป็นระดับวัน ไม่ใช่ “ขณะนี้มีเครื่องว่าง” และไม่ใช่รับประกันทุกช่วงในวันนั้น

### คำถามใหม่ที่ต้องถามเฉพาะถ้าต้องการตอบเรื่องการเข้าพื้นที่

> ช่วงพักเที่ยงหรือ Maintenance ที่ไม่เปิดให้จอง ศูนย์อนุญาตให้เข้ารอ/เยี่ยมชม/ติดต่อเจ้าหน้าที่ได้หรือไม่ และช่วงใด? ถ้าไม่มีนโยบายเรื่องนี้ ระบบจะตอบเฉพาะช่วงให้บริการ/จองที่ยืนยันแล้ว

คำถามนี้ต่างจากการขอให้ยืนยันซ้ำว่าจอง 12:00–13:00 ได้หรือไม่ และไม่ใช่ blocker ของการตอบว่าไม่มีช่องจองช่วงนั้น

## 5. กติกาแข่งขันและปุ่มควบคุม

### กติกา

มี competition 4 และ competition_rule 104 รายการ มี source edition แต่ validity ยัง unknown ใน metadata การตอบ “กติกาของรายการ/ฉบับที่เก็บไว้” ต่างจากรับรองว่าใช้กับการแข่งขันครั้งถัดไป

ทำเองได้:

1. รักษาชื่อเกม รายการ ปี/edition และลำดับ source clauses
2. แยก facet เช่น conduct, roster, protest, pause, equipment ไม่ดึงกติกาเกมอื่นแทน
3. รวมเงื่อนไข/ข้อยกเว้น/โทษที่เป็น dependency ของ proposition
4. แปลไทย–อังกฤษแบบรักษา meaning และคำบังคับ must/may/not/deadline

ถามผู้รับผิดชอบ **เมื่อจะอ้างใช้กับรายการใหม่โดยไม่มี source**:

> การแข่งขันที่กำลังถามใช้ rulebook ชื่อ/ปี/เวอร์ชันใด และมีประกาศแก้ไขเพิ่มเติมหรือไม่? ขอฉบับและวันมีผลที่ใช้จริงกับรายการนี้

ไม่ต้องถามกติกาใหม่สำหรับการอธิบาย source ฉบับเดิมที่มีอยู่แล้ว แต่ต้องระบุ edition ไม่เหมารวมว่าเป็นกติกาถาวรทุกงาน

### ปุ่ม

มี control_set 43 รายการ จุดที่อังกฤษว่างจริง 11 จุดอยู่ใน section labels ของ Mario Kart Live: Home Circuit ไม่ใช่ขาดคำแปลทุกเกม อาจแปลหัวข้อจากไทยได้โดยคง bindings เดิม แต่ห้ามอ้างว่าได้ตรวจปุ่มบนเครื่องจริงจากการแปล

หาก source ระบุ limitation หรือยังไม่ตรวจจริง ต้องแสดงข้อจำกัดนั้น การเติม button action จากความจำทั่วไปไม่เท่ากับข้อมูลของแพลตฟอร์ม/โหมดที่ศูนย์ใช้

## 6. Publication และการย้ายไปให้คนอื่นใช้

สิ่งที่ทำเองได้คือ schema/ref/source/validity checks, dispatcher parity, package manifest และตรวจว่า runtime เปิดใช้ profile ใด ข้อมูล draft ที่ใช้ทดสอบไม่ถือเป็น production approved เพียงเพราะคะแนนดี

การตัดสินใจที่ต้องมีผู้รับผิดชอบก่อน cutover:

> release/record revisions ชุดใดได้รับอนุมัติให้เป็นข้อมูลที่เปิดตอบผู้ใช้จริง และใครเป็นผู้อนุมัติข้อมูลราคา/นโยบาย/กติกาในชุดนั้น?

นี่เป็นคนละประเด็นกับการอนุญาตให้พัฒนาโค้ดต่อ งานวิเคราะห์และแก้ interpreter ทำได้โดยไม่อนุมัติข้อเท็จจริงแทนเจ้าของ

เอกสารชุดนี้ยังไม่ได้ยืนยันแพ็กเกจ portable ทุกแบบหลังการแก้ล่าสุด และไม่ได้ทำการติดตั้งใหม่หรือ cutover ระหว่างตรวจ Flow

## 7. ลำดับที่ลดภาระเจ้าของได้จริง

1. แก้ task recovery/field projection/short follow-up จากข้อมูลที่มีอยู่ก่อน ไม่โยนเป็นคำถามเนื้อหาให้เจ้าของ
2. ไล่ source และคำยืนยันเดิมที่มีอยู่ให้ครบก่อนออก owner question
3. ส่งเฉพาะคำถามที่มีผลต่อ task หรือ publication พร้อม record IDs/field ที่ติดและเหตุที่ source ตอบไม่ได้
4. แก้ข้อมูลด้วย stable ID + new revision + source pointer + review status ตามจริง ไม่แก้ log ทดสอบย้อนหลัง
5. ก่อนทดสอบครั้งถัดไป แยกโจทย์ current/historical/unknown/conflict เพื่อวัดการตอบที่ถูกสถานะ
