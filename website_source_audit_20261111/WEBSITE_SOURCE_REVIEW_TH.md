# ตรวจเว็บไซต์ต้นทาง PSU Esports — 11 พฤศจิกายน 2026

ขอบเขต: ตรวจหน้าจองและหมวดหลักของเว็บไซต์ประชาสัมพันธ์ รวมภาพราคา ไม่ใช่ตรวจครบทุกบทความ/ไฟล์แนบในเว็บไซต์ และยังไม่ได้แก้ owner DB หรือผลวัดที่ frozen

## สถานะการเข้าถึง

- เว็บไซต์จองตอบ HTTP 200 จากเครื่องและเก็บ HTML/text พร้อม hash ใน FETCH_MANIFEST.json
- ภาพราคาดาวน์โหลดและอ่านด้วยสายตาแล้ว เก็บ service_fee.png
- เว็บประชาสัมพันธ์อ่านได้บางหน้าจากระบบค้นหา/สำเนาที่เครื่องมือเว็บจัดเก็บ แต่การเปิดซ้ำบางครั้งได้502 และเครื่องนี้ resolve domain ไม่สำเร็จ อย่าเรียกทั้งหมดว่าเนื้อหาที่ fetch สด ณ วันนี้ วันที่ crawl ของแต่ละหน้าแตกต่างกัน
- `home` และหน้า `/` ที่เครื่องมือคืนมามีรายละเอียดต่างกัน จึงต้องแยก URL และเวอร์ชัน ไม่รวม inventory เป็นฉบับเดียวทันที

## จุดต่างจากฐานเดิมที่มีผลต่อ Flow

**คำยืนยันเจ้าของภายหลังการตรวจ:** ผู้ใช้แก้ความเข้าใจในบทสนทนาว่า ราคาจริงของนักศึกษาคือ0บาทและรูปยังไม่ได้เปลี่ยน ในบริบทนี้คือราคา PC สำหรับนักศึกษา PSU ที่เปรียบเทียบ20กับ0 จึงยึด0ตามคำยืนยันนี้ ไม่ให้ป้ายเก่าoverrideราคา เก็บหลักฐานใน OWNER_PRICE_CLARIFICATION.json เว็บไซต์ยังใช้เป็นลิงก์ประกอบข้อมูลศูนย์ แต่ไม่กล่าวว่ารูปเป็นหลักฐานของราคา0 และไม่ขยายคำยืนยันไปบริการหรือกลุ่มอื่นอัตโนมัติ

1. Rate PC นักศึกษา/บุคลากรใน DB เดิม amount_minor=0 แต่ภาพที่เชื่อมจากหน้าจองระบุ20 ภายหลังเจ้าของยืนยันราคา PC นักศึกษา PSU เป็น0และรูปยังไม่แก้ จึงแก้ conflict เฉพาะขอบเขตนักศึกษานี้ด้วย owner statement ไม่ใช้ภาพเก่าเปลี่ยนเป็น20 ส่วนขอบเขตบุคลากรให้รักษาหลักฐานเดิม ไม่ถือว่าคำยืนยันนักศึกษาครอบคลุมทุกกลุ่ม
2. หน้าจองที่อ่านครั้งนี้ใส่ Warzone ในรายการ PC #01 และ #02 แต่ข้อมูลเดิมเคยผูก TEKKEN8 และระบุว่าไม่มี Warzone ต้องตรวจ game_service ใหม่ตามเครื่อง ไม่คัด alias เดิมมารับรองรายการเกม
3. หน้า `/` กับ `/home` ที่เครื่องมือให้มามีจำนวนอุปกรณ์ต่างกัน เป็นคนละ snapshot/URL จึงยังไม่เลือกจำนวนชุดหนึ่งว่าเป็นสถานะปัจจุบันทั้งหมด
4. หน้า About/หน้าแรกให้หลักฐานผู้ดำเนินงานที่ชัดกว่า FAQ เดิมที่ยังผูก center ไม่ได้ สามารถสร้าง mapping proposal ตาม source ได้โดยไม่ hardcode คำตอบลอย ๆ
5. หลายคำตอบอาจมีข้อมูลต้นทางรองรับแล้ว แต่ pipeline ยังไม่ผูก record/field กับ section/URL และหน้าแชตแสดงเพียง draft label ปัญหานี้ต้องแก้การนำเข้าหลักฐานกับการแสดง citation ไม่ใช่กล่าวว่าทุกข้อไม่มีข้อมูล

## ขั้นต่อไปที่ใช้ข้อมูลนี้ได้จริง

1. สร้าง source records ต่อ section พร้อม canonical URL, retrieved_at, content hash, ข้อความ/ส่วนภาพ และ subject ID
2. ทำ field-level mapping ให้ service/platform/audience/time ตรง โดยเก็บ conflict เป็นรายการแยก
3. ทดลองใน DB สำเนาและให้ citations แสดงชื่อหน้า URL และ section ที่สนับสนุน claim นั้น ไม่ใส่หน้าแรกให้ทุก claim
4. เปลี่ยนข้อความ “ไม่มีข้อมูลยืนยัน” เป็นเหตุผลที่ตรงกรณี: ยังไม่ import / ขัดกับฉบับเดิม / ไม่รู้เงื่อนไข / หา source ไม่เจอ
5. ทดสอบคำถามที่เคยไม่มีคำตอบจาก source ใหม่ รวม wrong-target และข้อมูลที่เปลี่ยน ไม่ย้อนแก้ผลเก่าที่วัดแล้ว

ยังไม่ควรอ้างว่ามีคำตอบทุกเรื่อง เช่น สถานะเครื่องว่างต้องตรวจเวลาจริง, คู่มือปุ่มต้องอ่านภาพหรือเอกสารของเกม/รุ่นนั้น, ข้อมูลส่วนบุคคลที่ไม่เผยแพร่ไม่เกิดขึ้นเพียงเพราะเว็บไซต์มีหน้า Members
