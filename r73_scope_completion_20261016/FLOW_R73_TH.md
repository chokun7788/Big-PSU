# Flow R73 — ตอบ source ที่มี และระบุสิ่งที่ยังยืนยันไม่ได้ให้ตรงเรื่อง

## เป้าหมาย

ทำต่อจาก R72 โดยใช้ format กลางและเปิด LLM ทดสอบเฉพาะปัญหาที่เกี่ยวข้องในรอบนี้ เก็บ R72 และ log เก่าไว้ สำเนาที่แก้อยู่ใน R73

## หลักฐานก่อนแก้

- FAQ เรื่องคีย์บอร์ด/เมาส์ส่วนตัวมีคำตอบจากเจ้าของอยู่จริง แต่คำถาม permission ยังไปพึ่ง model selector
- Procedure เรื่องแนบสลิปผิดมี steps และช่องทางติดต่อที่ยืนยันไว้แล้ว
- โอนเกิน/โอนขาด/ผ่อน/เงินถึงบัญชี/อายุเด็ก ยังไม่พบคำตอบเฉพาะที่ยืนยันได้ในข้อมูลที่ตรวจ อย่าสรุปนโยบายจาก deadline หรือ refund ทั่วไป
- ขอสิทธิ์เครือข่ายผ่านระบบในรอบนี้แล้ว ยังไม่มี grant; คงเปิด LLM และเก็บผล transport ตามจริง

## ลำดับทำงาน

1. เก็บ source/code/data manifest และ backup SQLite ของ R72 ไป R73
2. เพิ่ม `query_profile` เป็น metadata ทางเลือกสำหรับ FAQ / policy / procedure เก่าที่ไม่กรอกต้องยังอ่านและแก้ผ่านฟอร์มได้
3. Metadata ระบุชนิดคำถาม permission/correction, เรื่องที่ใช้ตอบเป็นไทย/อังกฤษ, เจ้าของอุปกรณ์ personal/any และบริบท studio/competition คำตอบยังอ่านจาก fields จริงทุกครั้ง
4. ย้ายเฉพาะ metadata ของ FAQ อุปกรณ์ส่วนตัวและ procedure สลิปผิดที่มีหลักฐานชัด ค่า answer/steps/เงื่อนไข/แหล่งข้อเท็จจริงเดิมต้องเท่าเดิม ไม่สร้าง approval
5. เลือกจาก task + subject + ownership + context พร้อมกัน ห้ามใช้เพียง keyword keyboard หรือ wrong และห้ามเลือกเมื่อ metadata ชนกัน
6. ใช้ renderer และการตรวจหลักฐานเดิม ตั้ง requested fields ให้ตรงชนิดข้อมูล เก็บ selection audit ไม่ข้าม validity/withdraw/source checks
7. คำถามที่ยังยืนยันไม่ได้ให้บอกเรื่องที่ยังยืนยันไม่ได้และช่องทางจริง ห้ามถามชื่อเกมเมื่อผู้ใช้ระบุปัญหาเงินหรืออายุชัดอยู่แล้ว และห้ามใช้ retry แทน unknown ทุกกรณี
8. คำถามขาดข้อมูล เช่น จ่ายยอดผิดแต่ไม่ระบุเกิน/ขาด ให้ถามจุดที่ช่วยจำแนกสถานการณ์ พร้อมย้ำว่ายังยืนยันวิธีจัดการไม่ได้ ไม่รับปากคืนเงินหรือแก้รายการให้
9. คำถามผสมให้แต่ละส่วนมีสถานะ answer / partial / clarification / unconfirmed ไม่ทำให้ unknown ภายในกลายเป็น answer ทั้งประโยค
10. สร้าง contracts เนื้อหาจริง รวมคำปฏิเสธ source/citation/context ไม่ใช้เฉพาะ forbidden words; เก็บ baseline และแต่ละรอบแยก
11. ทดสอบข้อมูลใหม่และแก้ revision ใน fixture แยก ต้องใช้ profile เดิมกับชื่อ/ID/subject ใหม่ได้ และ unknown/conflict/withdraw ไม่ถูกอ่านเป็น known
12. ตรวจ regressions R72 เฉพาะกลุ่มที่อาจได้รับผล ไม่รัน full/legacy/OFF แล้วเขียนรายงานสิ่งที่ยังขาด

## ตรวจความเสี่ยงก่อนใช้

### รอบทบทวน 1 — ไม่ใช้ metadata เป็นข้อเท็จจริง

profile ใช้เลือก record เท่านั้น ไม่เก็บราคา/decision/วิธีคืนเงินไว้ใน router ไม่ให้ profile เปลี่ยนเงื่อนไข source และไม่เปิดให้โมเดลสร้าง policy เอง

### รอบทบทวน 2 — ป้องกันคำถามใกล้เคียง

ต้องกัน keyboard รุ่นอะไร / keyboard ของศูนย์ / หูฟังส่วนตัว / แข่งขัน / โอนยอดผิดกับแนบสลิปผิด / ผ่อนชำระกับ deadline คนละเรื่อง การปฏิเสธห้ามกลับขั้วความหมาย การถามหลายอุปกรณ์ต้องไม่ตอบเฉพาะชิ้นที่รู้แล้วถือว่าครบ

### รอบทบทวน 3 — การเพิ่มข้อมูลและส่งใช้งาน

เพิ่ม field แบบ optional และซ่อน metadata จากคำตอบทั้งหมดของผู้ใช้ แสดงชื่อช่องและตัวเลือกเป็นภาษาคนใน editor; ทดสอบรูปแบบผิดและข้อมูลเก่าที่ไม่มี field; การแก้ profile ต้องไม่ทำให้ข้อมูลเก่าหาย ไม่สร้างความเชื่อมตัวตนใหม่โดยเดา

## เกณฑ์การรายงาน

- แยก baseline/หลังแก้, ไทย/อังกฤษ, positive content/unknown/clarification/safety และ transport
- unknown ที่ตอบตรงเรื่องเป็นผลที่ถูกได้ แต่ไม่ใช่การยืนยันนโยบาย
- บททดสอบภายในไม่ใช่ผล browser/TCP/WordPress จริงหรือ owner approval
- งานที่ยังขึ้นกับโมเดลจริงและงาน Format ทุกหมวดยังคงเป็น backlog ไม่สรุปว่าครบทั้งระบบจากชุดย่อย

## ปรับจากผลใช้งานจริง

1. แยก temporal “แล้ว/then” ออกจากการเชื่อมสิ่งของด้วย “และ/and” เพื่อไม่ให้ขอแก้สลิปผิดถูกมองเป็นคำถามหลายอุปกรณ์
2. แยกคำถามผสมก่อนใช้ตัวกัน exception ของทั้งประโยค ไม่ให้คำว่า “ผ่อน” หรือ “สลิปผิด” กลบคำถามวิธีจ่ายอีกส่วน
3. ถ้าสองส่วนเป็น unknown เรื่องเดียวกัน เช่น อายุและผู้ปกครอง ให้รวมสถานะ unconfirmed เดียว ไม่สร้างคำตอบซ้ำ
4. ถ้าคำว่าโอนเงินจับ FAQ บัญชีได้แต่ไม่ครอบคลุมระยะเงินถึง ให้ทิ้ง candidate ที่ผิด scope และตอบข้อจำกัดตรงเรื่อง รวมทั้งภายในคำถามผสม ไม่แสดง candidate ที่ไม่ผ่าน validation ออกไป
5. ownership ต้องสัมพันธ์กับสิ่งของ ไม่ใช้ my จาก my booking มายืนยันว่า keyboard ของศูนย์เป็นของส่วนตัว และแยกคำถามซื้อ/ทำความสะอาดออกจากสิทธิ์นำมาใช้
6. เอกสาร preconditions ที่เป็นตัวเลือก issue ของ procedure แสดงชื่อสถานการณ์ภาษาคนตาม source ไม่แสดง field/operator/code ให้ผู้ใช้ และยังเก็บเงื่อนไขในหลักฐาน
7. ข้อมูลเก่าที่ไม่มี optional profile ต้องได้ unknown envelope ที่ note ถูก schema เมื่อเปิดแก้ใน owner form
8. Holdout พบ proof of payment ไม่ตรงคำ slip และ record ที่ถูกไม่มีใน candidate เดิม จึงเพิ่ม task metadata เป็น recall backstop ภายใต้ budget เดิม โดยต้องผ่าน semantic selection ไม่ตอบเองเพราะมี candidate เพียงชิ้นเดียว การเรียกโมเดลยังติดสิทธิ์และต้องทดสอบ field planner ต่อ
9. เพิ่มความหมายเปรียบเทียบยอด too low/high เป็น under/overpayment โดยยังคงสถานะนโยบายไม่ยืนยัน ไม่เพิ่มวิธีคืนเงินหรืออนุญาตโอนเพิ่มเอง
