# ผลจริงหลังเปิด Full access และสิ่งที่ยังผิด

## 1. คำตอบเรื่องสิทธิ์

รอบนี้เรียกจากเครื่องมือในแชทได้จริง: อ่านรายชื่อโมเดล Ollama, ตรวจ health ของ Chatbot, ส่งคำสั่งหยุด R78 ที่ยืนยันตัวตนได้, เปิด R78 ใหม่ และส่งคำถามผ่าน HTTP ได้ ไม่มี WinError 10013 ในรอบที่จบนี้

จึงยืนยันได้ว่าเงื่อนไขสิทธิ์หลังเปิด Full access ทำให้ workflow นี้เดินต่อได้ในรอบนี้ ไม่ได้พิสูจน์ว่าต้นเหตุของทุก 10013 ในอดีตเป็นส่วนใดของระบบปฏิบัติการ

R78 ที่ทดสอบคือ PID 41084, source fingerprint `94ff47522fbb2df31bd7890dfa23da13caed4c0b65cbfeb98d28aa61f1ea0b77`, LLM enabled=true, worker 45816/6516 พร้อมทั้งสองตัว จาก health ที่บันทึกในรอบนี้

## 2. ผลที่ต้องแยกสามระดับ

| ระดับ | ผลจริง | ความหมาย |
|---|---:|---|
| Ollama สร้าง READY | สำเร็จ HTTP 200, done=true | โมเดลสร้างข้อความจริงได้ |
| คำตอบบทสนทนา | 14/14 ตามเกณฑ์ชุดนี้ | ไทย 6/6 อังกฤษ 8/8 รวมการถามยืนยันและถามต่อ |
| selector เรียกโมเดล | 3 ครั้ง | 2 timeout; 1 ได้ response ตามรูปแบบ JSON แต่ binding ถูกปฏิเสธ |
| selector contract ที่ยอมรับการเลือกได้ | 0/3 | ห้ามใช้ 14/14 ไปอ้างว่า LLM ตีความผ่านทั้งหมด |

เกณฑ์บทสนทนากำหนดให้ถามยืนยันเมื่อยังไม่มีหลักฐานความหมายเพียงพอ เมื่อผู้ใช้เลือกแล้วจึงอ่านข้อมูลต้นทาง จึงมีผลคำตอบผ่านแม้ selector ล้มได้ การคืนค่าของตัวรันเป็น exit code 1 ในรอบนี้ถูกต้อง เพราะยังมี model selector failure ไม่ใช่ full system pass

## 3. Timeout ภาษาไทย — คำถามเดียวกันสองรอบ

คำถาม: `ผมเอาอุปกรณ์อินพุตส่วนตัวมาใช้ได้ไหม`

- รอบแรก HTTP 9.143 วินาที; selector retrieval 133 ms, model lock 40 ms, admission 2 ms, รอ HTTP ของ Ollama 6,418 ms แล้ว timeout
- รอบที่สอง HTTP 7.729 วินาที; retrieval 134 ms, model lock 1 ms, admission 1 ms, รอ HTTP ของ Ollama 6,016 ms แล้ว timeout

หลักฐานนี้ชี้ว่าเวลาหลักของ selector ไปอยู่ที่การรอคำตอบจาก Ollama มากกว่ารอคิวในแอป ยังแยก load/prompt processing/generation ของสองคำขอนี้ไม่ได้ เพราะไม่มี response envelope กลับมาถึงตัวตรวจภายใน deadline จึงไม่เติม model timing เป็นศูนย์หรือเดาว่า GPU/RAM เป็นสาเหตุแน่นอน

ชุด candidate ผสม profile กับนโยบายอื่นและข้อมูลเกม จึงไม่เข้า shortcut ของ R81 ต้องแก้ retrieval/prompt/ภาระ protocol ต่อจากหลักฐานนี้ ระบบ fallback ถามยืนยันหัวข้อคีย์บอร์ด/เมาส์ และตอบจาก source ได้เมื่อผู้ใช้ระบุว่าเป็นเมาส์หรือคีย์บอร์ดส่วนตัว

## 4. อังกฤษ — เลือก source ถูก แต่เหตุผลประกอบไม่ผ่าน

คำถาม: `I attached incorrect proof of payment. How do I fix it?`

โมเดลเลือก index 0 ซึ่งเป็น `procedure_wrong_slip` ถูกตัว แต่ binding คืนค่า:

```json
{
  "task_span": "i attached incorrect proof of payment. how do i fix it",
  "subjects": [{"subject_index": 0, "span": "slip", "relation": "equivalent"}],
  "ownership": "studio"
}
```

ระบบปฏิเสธด้วย `unsupported_task_span` และ `semantic_selection_accepted=false` นอกจากนี้ subject span `slip` ไม่ได้ปรากฏในคำถามผู้ใช้ โมเดลนำชื่อแนวคิดจาก candidate มาใส่ในช่องที่สัญญากำหนดให้คัดจากคำถามโดยตรง การเลือก source ถูกจึงยังใช้ binding นี้เป็นหลักฐานไม่ได้

คำขอนี้ใช้ HTTP จาก selector ประมาณ 3.069 วินาที; Ollama load 31 ms, prompt_eval 216 ms, generation 2,389 ms; 620 prompt tokens และ 102 output tokens ยืนยันว่าโมเดลตอบกลับจริง แต่ไม่ถือว่า semantic contract ผ่าน ระบบจึงถามยืนยัน แล้วผู้ใช้ตอบ yes ก่อนอ่านขั้นตอนส่งสลิปให้เพจตาม source

ไม่ผ่อน validator ให้ยอมรับข้อความที่ผู้ใช้ไม่ได้พูดเพียงเพื่อให้คะแนนสูงขึ้น และไม่เพิ่ม alias ของคำถามตัวอย่างนี้

## 5. เวลาเปิดโมเดลและเวลาแชท

- READY ใช้ HTTP 39.812 วินาที โดย model load ประมาณ 34.779 วินาที เป็นช่วงเตรียมโมเดลก่อนเริ่มชุดคำถาม ไม่ใช่เวลาตอบปกติทุกครั้ง
- หลัง warm-up: ไทยมัธยฐาน 1.998 วินาที สูงสุด 9.143; อังกฤษมัธยฐาน 2.159 วินาที สูงสุด 10.076
- คำถามอังกฤษที่ข้าม selector ครั้งแรกยังใช้ 10.076 วินาที แต่ selector เองใช้เพียงประมาณ 309 ms ส่วนที่เหลือจึงอยู่นอก selector นี้ ยังไม่ได้แจกแจงทุก stage ให้ยืนยันสาเหตุ
- คำถามเดียวกันอังกฤษรอบหลังใช้ 1.183 วินาที; ไม่เอาคู่นี้ไปคำนวณ speedup ที่อ้างใช้ได้ทั่วไป เพราะสถานะ cache/startup ต่างกัน
- “วันนี้เปิดไหม” ใช้ 0.479 วินาที ตอบตรงว่า “วันนี้วันที่ 17 ตุลาคม 2569 ไม่เปิดให้บริการครับ”; อังกฤษใช้ 1.009 วินาที ตอบ date + closed ตรงรูปแบบที่ขอ

เป็นตัวอย่าง 14 ข้อความ หลัง warm-up ไม่ใช่ benchmark ความจุหรือ full corpus

## 6. ปัญหาของตัวรันทดสอบที่พบและปรับ

เก็บรอบไม่สำเร็จไว้ครบ:

1. `20261017T073733Z-7a68ae`: ส่ง shutdown สำเร็จ แต่ตัวตรวจใช้ probe สั้นหนึ่งวินาทีและยังยืนยัน shutdown ไม่ได้ จึงไม่ได้ทดสอบคำถาม ต่อมาพิสูจน์ว่าโปรเซสเก่าปิดแล้ว ปรับเวลาตรวจและบันทึกแต่ละรอบรอไว้ ไม่บังคับ kill
2. `20261017T074251Z-936cb6`: startup launcher เกินเพดาน 100 วินาทีของตัวรัน แต่โปรเซสแชทเปิดสำเร็จในภายหลัง พิสูจน์ด้วย `POST_STARTUP_HEALTH.json` จึงใช้โปรเซสนั้นต่อได้ รอบนี้ไม่มีคำถามให้คะแนน
3. `20261017T074528Z-4c2b1f`: reuse แชทที่พิสูจน์ fingerprint/LLM ON แล้ว และทดสอบครบ 14 ข้อความ

หลังอ่านผล ปรับเฉพาะตัวรันให้รอเริ่มบริการได้ 180 วินาที และแสดง binding rejection แยกจาก schema success เพิ่ม ไม่เปลี่ยน deadline ตอบคำถามของผลิตภัณฑ์ ไม่เปลี่ยน source code R78 เพิ่มในเทิร์นนี้ ชุดตรวจตัวรันล่าสุดผ่าน 24/24 ด้วย fixtures การเริ่มบริการแบบ cold หลังปรับเพดาน 180 วินาทียังไม่ได้รันซ้ำ

ผล raw RESULTS.json/CHAT_TURNS.jsonl ของรอบที่จบเป็นเวอร์ชันก่อนเพิ่มช่อง binding_rejections สรุปหลังตรวจในเอกสารนี้และ REVIEW.json อ้าง audit เดิมโดยไม่แก้ raw log และไม่ได้รันคำถามใหม่เพื่อเปลี่ยนคะแนน

## 7. งานถัดไปจากผลจริง

1. ลด candidate ที่ไม่มีหลักฐาน topic support และตรวจข้อมูลซ้ำ โดยไม่ตัด source ที่ถูกจากเพียงคะแนนอักษร ไม่เพิ่ม alias เฉพาะคำถามนี้
2. ปรับ selector protocol ให้โมเดลชี้ข้อความจาก input ได้ตรง เช่น binding ที่อ้างช่วงข้อความซึ่งตรวจได้ พร้อม contrast cases proof of identity/proof of payment ป้องกันแก้ความถูกต้องด้วยการผ่อนเงื่อนไข
3. วัดคำขอไทยด้วย prompt เดียวกันเพื่อแยก prompt-eval และ generation ภายในกรอบทดสอบที่ชัดเจน ก่อนเลือกวิธีลดภาระ ไม่เพิ่ม deadline ของแอปโดยเดา
4. ทดสอบเฉพาะส่วนที่ปรับซ้ำก่อนขยายเป็น full test
