# สิ่งที่ต้องทำต่อหลัง R75

รายการนี้คือประเด็นที่ตรวจพบหรือยังไม่มีหลักฐานรับรอง ไม่ใช่การประกาศว่าทุกประเด็นล้มเหลวอยู่ และ targeted tests ที่ผ่านไม่เท่ากับ full-system accuracy

## ลำดับ 1 — ตรวจ semantic model กับคำถามจริงและคู่ลบ

**สถานะ:** ยังติดสิทธิ์การเรียกโมเดลจากเครื่องมือ WinError 10013 ขอสิทธิ์ผ่านระบบแล้วไม่ได้รับเพิ่ม R75 มีเส้นทางถามยืนยันที่ใช้งานผ่าน dispatcher ได้ระหว่างโมเดลไม่พร้อม

**ต้องทำ:** เมื่อมีสิทธิ์ ให้โมเดลสร้างแผนเองในคู่ payment proof/identity proof/amount/file format/deadline/competition ทั้งไทยและอังกฤษ เก็บ candidate IDs/scores, proposal, quoted spans, scope, transport/schema/semantic result และคำตอบ source แยกกัน วัดเวลา prompt/queue/model/total จริง

**ทำเองได้:** เตรียมและรัน targeted cases วิเคราะห์ false match/false abstention ปรับการเลือกและ guard จากผลจริง โดยไม่เปลี่ยนข้อเท็จจริง

**สิ่งที่ต้องมี:** ช่องทางเรียกโมเดลที่ได้รับอนุญาต ไม่ใช่ owner policy ใหม่ ห้ามอ้างความเร็วจาก mocked responses และห้ามใช้ทางอื่นข้ามข้อจำกัดสิทธิ์

## ลำดับ 2 — พัฒนา subject meaning เพื่อให้ตอบทันทีได้มากขึ้น

**สถานะ:** R75 ถามเพิ่มสำหรับ semantic-only profile; literal task/subject เดิมตอบได้ตามเดิม quote validation ยังไม่ใช่ independent semantic verification

**ต้องทำ:** ออกแบบ optional definition/typed constraints ที่อิง source ใน format กลาง เช่น ระบุว่าเป็นหลักฐานชำระหรือหลักฐานตัวตน เป็นขั้นตอนแก้ไขหรือข้อกำหนดไฟล์ ใช้ร่วมกับ retrieval/model และเก็บ unknown เมื่อกรอกไม่ครบ ทดลองกับ fixtures หลาย concept ที่ไม่ได้ใช้สร้างตัวแก้ก่อน ไม่บังคับเจ้าของกรอก aliases ทุกประโยค

**ทำเองได้:** ออกแบบ schema/form/validator/isolated fixtures และทดสอบ source update/withdraw/contradiction

**เงื่อนไข:** ต้องไม่เติมความหมายหรือข้อจำกัดเกิน source การขยายข้อมูลจริงส่วนที่ source ไม่ชัดต้องคง unknown/รอเจ้าของ

## ลำดับ 3 — บทสนทนาปฏิเสธพร้อมคำถามใหม่ในข้อความเดียว

**สถานะ:** yes/no/เลข/ชื่อหัวข้อและการเปลี่ยนเรื่องผ่านชุดนี้แล้ว; “No, I mean …” ปิดหัวข้อเก่าได้ แต่ยังขอให้ระบุเรื่องใหม่อีกครั้ง ไม่ได้ตอบรายละเอียดหลัง I mean ในเทิร์นเดียว

**ต้องทำ:** แยก negative acknowledgement ออกจากคำถามใหม่ ส่งเฉพาะส่วนที่ผู้ใช้ระบุไปหาข้อมูล โดยกันการเสนอ record ที่เพิ่งถูกปฏิเสธซ้ำในเทิร์นนั้น ตรวจ “ไม่ใช่ … หมายถึง …”, “ไม่ใช่อันนี้”, yes-but/ใช่แต่มีเงื่อนไข, เปลี่ยนภาษา และคำตอบสั้นพิมพ์ผิด

**ทำเองได้:** เพิ่ม dialogue parser/state checks และทดสอบผ่าน actual handler แบบ memory; ทดสอบ browser/restart เมื่อช่องทางพร้อม

## ลำดับ 4 — การค้นเมื่อข้อมูลเพิ่มมากและการเสนอหัวข้อที่ตรงเรื่อง

**สถานะ:** 13 compatible profiles เลือกได้ครบผ่าน pagination แล้ว แต่ model top-k ยังจำกัด และเมนูจาก task/context อย่างเดียวอาจเสนอเรื่องที่ผู้ใช้ไม่ได้ตั้งใจถาม

**ต้องทำ:** วัด recall@k กับข้อมูลใหม่หลายจำนวน จัดหมวด/definition/index ก่อน rerank และปรับ prompt budget ไม่ให้หน้าต้นของ DB ตัดสินผล พัฒนาการจำกัดขอบเขตศูนย์โดยไม่ปิดกั้นคำถามบริการใหม่ ไม่ใช้เพียง wrong/แก้ แล้วถือว่าเกี่ยวกับสลิป

**ทำเองได้:** สร้างข้อมูลตัวอย่างแยก วัด recall/omission/ordering/performance และปรับ index, pagination UX, qualifier selection

**ข้อจำกัดปัจจุบัน:** การเลือกได้ทุกหน้าผ่านเมนูไม่ใช่หลักฐานว่าโมเดลค้นทุกหัวข้อเจอ และยังไม่วัดจำนวนข้อมูลหลักพันหรือหลายคนพร้อมกันใน R75

## ลำดับ 5 — ขอบเขตย่อย เงื่อนไข และความขัดแย้งใน source

**สถานะ:** direct profile ยังอาศัย task+subject ที่ประกาศ ไม่ได้เข้าใจทุกข้อยกเว้น/condition ที่เพิ่มใหม่ การแก้ grammar correct ไม่ครอบคลุมทุกภาษาหรือทุก property question

**ต้องทำ:** เพิ่ม contrast cases เรื่อง file requirements vs correction, payment amount vs slip, user ownership, competition vs studio, cancellation vs paid reschedule และคำถามหลายเงื่อนไข ตรวจ duplicate records/คำแปล/validity ที่ขัดกันก่อนเลือก source ไม่ใช้ตัวเลือกแรกหรือ title เหมือนกันแทนการตัดสินขอบเขต

**ทำเองได้:** ทำ source-consistency audit, classify failures, renderer/coverage tests และปรับส่วนที่หลักฐานยืนยันได้ เก็บข้อมูลเดิมไว้

**ต้องเจ้าของเมื่อ:** เอกสารสองฉบับให้ policy จริงขัดกัน หรือ source ไม่มีข้อสรุป ห้ามเลือกนโยบายแทนจากคะแนน retrieval

## ลำดับ 6 — นโยบายที่ข้อมูลยังไม่ยืนยัน

**ยังต้องคำตอบเจ้าของ:** โอนเกิน/ขาดจัดการอย่างไร, ผ่อนชำระ, ระยะเงินถึง/ตรวจชำระ, อายุและผู้ปกครอง รายละเอียดคำถามมีใน `r73_scope_completion_20261016/OWNER_QUESTIONS_R73_TH.md`

**ทำเองได้ก่อน:** รักษา unknown/unconfirmed ให้ตอบตรงเรื่องและไม่รับปากคืนเงิน/ให้โอนเพิ่มหรืออนุญาตเด็กเอง เพิ่ม fixtures หลังได้รับคำตอบจริง

เรื่อง 12:00–13:00 ไม่เปิดจอง และ VR 30 นาทีใช้ occupancy เต็มชั่วโมงเป็นข้อสรุปเดิม ไม่เปิดถามเจ้าของซ้ำ การตรวจสถานะจองจริงที่ผู้ใช้ยืนยันแล้วก็ไม่ถูกนับเป็นปัญหาใหม่จากรอบนี้

## ลำดับ 7 — ตรวจส่งใช้งานและแพ็กเกจ

**สถานะ:** R75 เป็น working copy ใช้ runtime จาก R69, DB เป็น draft preview, approvals/active ไม่เปลี่ยน ยังไม่ได้อัปเดต portable packages หรือเว็บที่เปิดอยู่โดยอัตโนมัติ

**ต้องทำ:** หลังเส้นทางนิ่ง ตรวจ actual browser/TCP/โมเดลจริงและ state หลัง restart, ทดสอบภาษาไทย/อังกฤษเฉพาะส่วนใหม่, ตรวจ publish/rollback/เจ้าของแก้ข้อมูล และสร้างแพ็กเกจสองแบบตามงานเดิมพร้อมทดสอบบนสำเนาที่สะอาด

**ทำเองได้:** เตรียม packaging/manifest/health/smoke scripts และใช้ fixture ก่อน; การเชื่อมต่อจริงต้องมีสิทธิ์และสภาพแวดล้อมพร้อม

ภาษาอังกฤษเดิมที่ผู้ใช้แจ้งว่าผ่านยังมีสถานะตามนั้น รอบนี้ไม่อ้างว่าทั้งระบบอังกฤษผิดหรือขอให้ตรวจใหม่ทั้งหมด แต่คำตอบ/metadata ภาษาอังกฤษที่เพิ่มหรือเปลี่ยนใหม่ยังต้องอยู่ใน targeted regression

## ลำดับ 8 — ความเร็วและหลายผู้ใช้

**สถานะ:** R75 ไม่ใช่ load test ไม่สรุปจำนวนคนสูงสุดหรือเวลาจาก fixture และหนึ่งรอบยืนยันเพิ่มเป็นต้นทุนของ flow ปัจจุบัน

**ต้องทำ:** เมื่อเรียกโมเดลจริงได้ ค่อยวัด concurrency 1/2/4/… ตามขอบเขตที่ปลอดภัย แยก static source answer, semantic selection, field planning และ live booking ใช้ผล queue/model/total แยกกันก่อนปรับ parallelism/cache/batching

**ทำเองได้:** สร้าง workload และวิเคราะห์ ไม่เปิด full ชุดใหญ่หรือ stress เว็บจริงโดยไม่จำเป็นระหว่างยังแก้ routing
