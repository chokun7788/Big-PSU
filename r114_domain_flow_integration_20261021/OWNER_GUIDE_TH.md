# วิธีใช้ Flow กลาง R114 และเพิ่มข้อมูล

## เปิดตัวทดลอง

เปิด `START_R114_PREVIEW.cmd` ในโฟลเดอร์นี้ โปรแกรมเปิดแชทที่พอร์ต **8134** และหน้าจัดการข้อมูลที่ **8135** พร้อมสิทธิ์เฉพาะเครื่อง หน้าเจ้าของต้องเปิดผ่านตัวเริ่มระบบเพื่อรับสิทธิ์ ไม่ส่งลิงก์ที่มี token ให้ผู้อื่น

ตัวนี้ใช้ฐานข้อมูลใน `system/data/knowledge/common.sqlite` ของ R114 และเก็บ log ใหม่ใน `runtime/วันเวลา/` ระบบเดิม R78 และแบบสอบถามพอร์ต 8120 ยังเป็นคนละชุดกัน ถ้าพอร์ตถูกใช้อยู่ ตัวเริ่มระบบจะหยุดและแจ้งให้ตรวจโปรแกรมเดิมก่อน

เมื่อเลิกใช้ ให้เปิด `STOP_R114_PREVIEW.cmd` โปรแกรมจะตรวจ PID กับคำสั่งของตัวที่เริ่มไว้ก่อนหยุดสองพอร์ตนี้

แชทนี้เป็น **preview ของ draft** ข้อมูลที่บันทึกใหม่จึงนำมาทดลองถามได้ทันทีโดยไม่ต้องเผยแพร่ก่อน การทดสอบที่ผ่านยังไม่ใช่การอนุมัติข้อมูลแทนเจ้าของ ไม่มีการติดตั้งทับระบบเดิม

## ขั้นตอนสำหรับเจ้าของ

1. เลือกชนิดข้อมูลตามตารางด้านล่าง ใส่ชื่อไทย/อังกฤษและคำเรียกอื่นที่ผู้ใช้ใช้จริง
2. กรอกค่าที่ทราบ พร้อมหลักฐาน/หมายเหตุและวันที่มีผล กรณีไม่ทราบให้ใช้สถานะ unknown การเว้นไว้ไม่ใช่คำตอบว่าไม่มีหรือไม่ได้
3. บันทึก draft แล้วลองถามใน preview ทั้งชื่อเต็มและชื่อย่อ รวมถึงคำถามที่ข้อมูลไม่ครอบคลุม
4. ตรวจเงื่อนไขทั้งหมด เช่น กลุ่มผู้ใช้ หน่วยราคา เกม/แพลตฟอร์ม รุ่นกติกา และช่วงเวลา
5. เมื่อข้อมูลถูกต้อง เจ้าของจึงอนุมัติ revision นั้นและเผยแพร่ตามกระบวนการเดิม การแก้ draft ภายหลังไม่เปลี่ยนฉบับ published จนกว่าจะอนุมัติ/เผยแพร่ใหม่
6. การถอนข้อมูลมีผลกับคำถามถัดไป ประวัติ revision และหลักฐานยังเก็บไว้

## ควรเพิ่มข้อมูลแบบใด

| สิ่งที่ต้องการให้แชทตอบ | ชนิดข้อมูล/ความสัมพันธ์ที่ต้องมี | จุดที่มักตกหล่น |
|---|---|---|
| ที่อยู่ แผนที่ ช่องทางติดต่อ | center / contact / facility | แยกที่ตั้งศูนย์กับที่จอดรถ/จุดพัก |
| บุคลากรและหน้าที่ | person พร้อมขอบเขตที่เปิดเผยได้ | ไม่ใส่ข้อมูลส่วนตัวในช่องทางสาธารณะ |
| อุปกรณ์ จำนวน สเปก จำนวนคนเล่น | equipment_model / resource / zone และความสัมพันธ์อุปกรณ์ | จำนวนเครื่อง จำนวนจอย และที่นั่งห้องเป็นคนละหน่วย |
| เกมที่มีให้เล่นบนเครื่อง | game **และ game_service ที่ offered=true** | เพิ่มชื่อเกมอย่างเดียวไม่ยืนยันว่าศูนย์ให้บริการเกมนั้นบนเครื่องใด |
| จำนวนผู้เล่นของเกม | game_mode พร้อม game_id/แพลตฟอร์ม/โหมด | ไม่ใช้จำนวนที่นั่งห้องแทนจำนวนผู้เล่นเกม |
| ปุ่มควบคุม | control_set / binding | เกม แพลตฟอร์ม และ action ต้องตรงกัน |
| ราคาปกติ | service + audience + rate | ระบุหน่วยต่อคน/กลุ่ม/รอบ ระยะเวลา สกุลเงิน และกฎคิดเศษเวลา |
| ราคาเหมาจ่าย | rental_package + zone + audience | ครึ่งวัน/เต็มวัน อุปกรณ์ที่รวม จำนวนที่นั่งและเงื่อนไข ต้องไม่เอาราคารายคนมาคูณแทน |
| วิธีจอง เปลี่ยน/ยกเลิก | procedure หรือ FAQ ที่ระบุสถานการณ์ชัด | จ่ายแล้ว/ยังไม่จ่าย เปลี่ยนวัน/เครื่อง และเหตุขัดข้องอาจใช้คนละเงื่อนไข |
| การจ่ายเงินและเงินเกิน/ขาด | policy / FAQ แยกแต่ละสถานการณ์ | เครดิตเงินเกินไม่ได้ยืนยันวันหมดอายุ หากยังไม่มีนโยบายวันหมดอายุ |
| กฎใช้บริการ | policy พร้อม decision, conditions_all และ exceptions | การอนุญาตโดยมีเงื่อนไขต้องเก็บทั้งเงื่อนไขและข้อยกเว้น |
| เวลาเปิดและวันปิด | schedule / closure | เวลาเปิด เวลาให้จอง และบำรุงรักษาต้องแยกกัน |
| เครื่องว่างจริงหรือไม่ | live_binding + provider + status_mapping + freshness policy | ต้องเชื่อมข้อมูลสดที่ใช้งานได้ ตารางเวลาคงที่ไม่ยืนยันว่าเครื่องว่าง |
| กติกาแข่งขัน | competition + competition_rule + dependencies | ระบุรายการ ปี/ฉบับ เกม และข้อกติกาที่ต้องอ่านประกอบ |
| ข่าว/กิจกรรม | news พร้อมวันจัด/วันสมัคร/ลิงก์และช่วงมีผล | ไม่ใช้ข่าวจำลองหรือข้อมูลคนละปีแทนข่าวจริง |

## ข้อมูลที่ย้ายเข้าตัวทดลองแล้ว

- ข้อมูลเจ้าของที่มีหลักฐานและรายการเหมาจ่ายถูกเพิ่มเป็น draft ใน candidate พร้อมตัวชี้กลับไปยังต้นทาง
- คำยืนยันใช้อัตราเดิมและหน่วยรายคนผูกกับ hash ของอัตราที่เจ้าของยืนยัน ถ้าแก้ราคาเอง คำยืนยันเก่าไม่อนุมัติราคาใหม่โดยอัตโนมัติ
- รายการราคาเหมาจ่ายซ้ำที่ตรวจว่า tuple และจำนวนเงินตรงกันถูกถอนใน candidate เท่านั้น ประวัติเดิมยังอยู่
- ข้อมูลบางส่วนยังเป็นข้อความกติกา/FAQ ที่มีขอบเขตกำกับ การนำเข้าไม่ได้หมายความว่าทุกเงื่อนไขถูกแปลงเป็นสูตรหรือ predicate ที่คำนวณได้แล้ว

## ข้อจำกัดที่ต้องรู้

การเพิ่ม record ที่มีชื่อเฉพาะใหม่และสัมพันธ์ตาม schema ใช้โค้ดเดิมได้ แต่คำถามที่มีความหมายธุรกิจใหม่ ซึ่ง schema/ตัวอ่านยังไม่รองรับ อาจต้องขยายตัวอ่านด้วย ไม่ควรเติมข้อเท็จจริงที่ไม่ทราบเพื่อให้คะแนนผ่าน

LLM เปิดใช้งานแบบมีเงื่อนไข งานที่อ่านและคำนวณจาก field ได้ตรงจะไม่เรียกโมเดล งานที่กำกวมให้โมเดลเลือกหลักฐานภายในขอบเขตเท่านั้น โมเดลไม่สร้างราคา กติกา หรือสถานะเครื่องเอง

คำว่า “บุคคลภายนอก” อาจครอบคลุมหลายกลุ่มราคา จึงไม่ถือว่าเป็น General Adult โดยอัตโนมัติ เลือกกลุ่มตามเงื่อนไขจริง และบริการที่มีทั้งรอบ 30/60 นาทีควรระบุ เช่น “VR สำหรับ General Adult 2 คน 2 รอบ รอบละ 30 นาที” หรือเติมนาทีต่อรอบเมื่อแชทถามเพิ่ม
