# บันทึกตรวจทาน Flow R71

สถานะ: ตรวจทานเอกสารก่อนเริ่ม implementation ไม่ใช่ผลทดสอบว่าโค้ดแก้แล้ว

## รอบตรวจ 1 — ความตรงกับหลักฐานและความหมายที่อาจผิด

อ่านรายงาน R70, ตัวอย่างคำตอบ, candidate inspection และ Flow ฉบับแรก เทียบกับพฤติกรรมใน reader/planner/query scope

สิ่งที่แก้ในเอกสาร:

- แยก protocol ที่ไม่ตรงจากการเลือกเนื้อหาผิด ไม่เหมารวมคะแนน 8.95% เป็นความถูกต้องเชิงเนื้อหา
- ระบุว่า ON มี model transport 253 ครั้งแต่สำเร็จ 0 จึงไม่ประกาศว่า LLM ผ่าน
- เพิ่มเส้นทางเมื่อแผนหรือคำตอบไม่ผ่านใน diagram ให้ไปตอบส่วนที่ตรวจผ่าน/ขอชี้แจง แทนส่งต่อเหมือนผลผ่านเสมอ
- เพิ่มการแยกคำขอนอกขอบเขตจากข้อมูลศูนย์ที่ยังไม่ทราบ และคู่ตัวอย่าง NBA กับเกม NBA 2K
- แยกกฎกันช่อง VR 30 นาทีเต็มชั่วโมงออกจากการคิดราคาซึ่งต้องใช้หลักฐานคนละส่วน
- แก้เลขหัวข้ออ้างอิงรายการคำถามเจ้าของให้ถูกต้อง

ผล: สาเหตุและจำนวนใน Flow อิงผลเดิม และไม่สร้างนโยบายหรือผลทดสอบใหม่ขึ้นมา

## รอบตรวจ 2 — ลำดับพึ่งพาและผลข้างเคียงของแนวทางแก้

ตรวจลำดับ S00–S14 รวมทั้ง backlog และกรณีลบที่อาจเกิดจากการแก้

สิ่งที่แก้/ระบุให้ชัด:

- การเชื่อม identity ต้องดู edition/platform/source/authority ไม่ใช้ความคล้ายชื่ออย่างเดียว
- unknown จากการย้ายไม่ครบไม่เท่ากับ unknown ที่เจ้าของถอนหรือไม่รับรองใหม่ ห้ามใช้ known เก่าทับโดยไม่มีหลักฐาน
- preview และ production resolve snapshot คนละกติกา การ save draft ไม่ทำให้ production อ่าน draft heads
- เพิ่มการตรวจ field ยาว/ข้อความท้าย และ excerpt ของ candidate เพื่อไม่ให้การจำกัดบริบททำให้ข้อมูลที่ย้ายครบหายตอนค้นอีก
- ไม่แก้ retrieval ด้วยการส่งข้อมูลทั้งฐาน และไม่เพิ่ม alias ทีละรูปประโยคเป็นแนวทางหลัก
- รอบ 1 ของ backlog เป็นการเตรียมแกนข้อมูล/needs ยังไม่ประกาศว่าปัญหาผู้ใช้หายจนผ่านขั้นเลือกแผนและประกอบคำตอบ
- แยกการเปรียบเทียบ R70 โมเดลไม่พร้อมจากการวัดโค้ดใหม่เมื่อโมเดลพร้อม ต้องมี paired subset ที่สภาพแวดล้อมตรงกัน
- ชุดทดสอบ 303 model-retest อาจซ้ำกับชุดพัฒนา/holdout จึงต้องรายงาน union จริง

ผล: แต่ละขั้นมี input/output/ประตูผ่าน และอุปสรรคโมเดลไม่บังคับให้หยุดงานเทคนิคอื่นทั้งหมด

## รอบตรวจ 3 — ความครบของงานและเอกสารสำหรับลงมือ

ตรวจขั้นตอนและจุดส่งมอบ พร้อมตรวจลิงก์และจำนวนกับไฟล์ผลจริง โดยผลอัตโนมัติบันทึกใน DOCUMENT_QA.json

รายการตรวจ:

- มี S00–S14 ไม่ซ้ำและเชื่อมกับ T00–T14 ใน backlog
- มีแผนทดสอบบวก/ลบ 28 ครอบครัว รวมคำเกริ่น สะกดผิด เปลี่ยนความหมาย ถามต่อ และแก้ข้อมูล
- ครอบคลุม registry ทั้ง 24 หมวด และระบุหมวดที่ไม่มีข้อมูลจริงว่าใช้ fixture แยก
- ทุกงานเป็นสถานะวางแผน ไม่มีการอ้างว่าผลทดสอบใหม่ผ่านแล้ว
- ลิงก์ไปหลักฐานและไฟล์โค้ดปัจจุบันมีอยู่จริง
- คำถามเจ้าของไม่ถามพักเที่ยง/VR/สถานะที่เคยรับรองซ้ำ แต่แยกเรื่องวันมีผล/นโยบายขัดกันที่ยังขาด
- ไม่มีข้อสรุปว่าครบทุกบรรทัดของ TXT กติกาที่หาย หรือแปลง 166 fact cards เป็น facts ใหม่
- โค้ดและฐาน R69 รวมทั้งรายงาน R70 ยังตรง baseline ที่บันทึกไว้

ผลตรวจเอกสารไม่ได้รับรองคุณภาพของ implementation ในอนาคต ขั้นทดสอบ S13 และประตูเผยแพร่ S14 ยังต้องทำจริงเมื่อเริ่มลงมือ

## สิ่งที่คงเป็นข้อจำกัด

- การเข้าถึงโมเดลและ HTTP ต้องตรวจเมื่อมีสิทธิ์ ไม่แก้ด้วยการหลบ sandbox
- ข้อมูลที่ต้องตัดสินนโยบายยังใช้คำยืนยันของเจ้าของ
- เกณฑ์ข้อความและ source ต้องเพิ่มอย่างเป็นอิสระจาก parser ที่กำลังพัฒนา เพื่อไม่ให้ระบบตรวจตนเองด้วยความผิดชุดเดียวกัน
- การถามสำนวนใหม่ทุกแบบยังต้องเก็บข้อผิดพลาดและปรับเป็นรอบตามหลักฐาน ไม่รับรองว่าเอกสารที่ทบทวนแล้วกำจัดข้อผิดพลาดทั้งหมดได้
