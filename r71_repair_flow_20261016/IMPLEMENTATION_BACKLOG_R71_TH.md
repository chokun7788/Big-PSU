| ครอบครัว | ตัวอย่างคำถาม/บทสนทนา | สิ่งที่ต้องตรวจ | คู่ลบที่ต้องกัน |

## 3. ตรวจความครอบคลุม Format ทั้ง 24 หมวด

หมวดที่ไม่มีข้อมูลจริงใช้ fixture แยกเมื่อจะตรวจกลไก ข้อมูลตัวอย่างไม่เข้าฐานใช้งาน และไม่สร้าง owner attestation/approval แทนมนุษย์

| หมวด | ความหมายที่ต้องรักษา | กรณีที่ต้องกัน |
|---|---|---|
| center | ชื่อ ผู้ดำเนินการ ที่ตั้ง เวลาอ้างอิงศูนย์ | ที่อยู่ไม่กลายเป็นเวลาเปิด/สถานะสด |
| contact | ช่องทาง/value/purpose | ไม่สร้างเบอร์หรือเวลาตอบกลับ |
| facility | ที่จอดรถ ที่นั่งพัก และข้อมูลที่ระบุจริง | ไม่อนุมานจำนวนที่จอดหรือสิทธิ์เข้าถึง |
| zone | โซนและความสัมพันธ์กับบริการ | capacity ไม่เท่ากับเครื่องว่าง |
| equipment_model | รุ่น สเปก วิธีใช้ | ไม่จับคู่ serial/resource จริงโดยเดา |
| resource | ตัวเครื่อง/ทรัพยากรที่มี ID | label คล้ายกันไม่แปลว่าเป็นเครื่องเดียวกัน |
| service | ตัวเลือกที่ผู้ใช้จอง | ไม่สับสนกับรุ่นอุปกรณ์หรือโซน |
| game | เนื้อหาและคุณสมบัติตัวเกม | มีระเบียนเกมไม่เท่ากับเปิดให้เล่นที่ศูนย์ |
| game_service | เกมในบริการ/เครื่องที่ศูนย์บันทึกไว้ | รายการติดตั้งไม่ใช่ live availability |
| game_mode | รูปแบบเล่น/จำนวนผู้เล่นที่ยืนยัน | ไม่เดา 4 คนจากชื่อเกมหรือชื่อเครื่อง |
| control_set | platform/preset/bindings/หมายเหตุ | ไม่ผสมผังข้ามแพลตฟอร์มหรือตัด modifier |
| audience | กลุ่มผู้ใช้และเงื่อนไขสิทธิ์ | ไม่เหมาว่าบุคคลภายนอกทุกคนเป็น General Adult |
| rate | ราคา หน่วย กลุ่ม และ validity | ไม่ใช้ expired เป็นปัจจุบันหรือปัด occupancy เป็นราคา |
| rental_package | แพ็กเกจ ขอบเขต เวลา/ระยะเวลาจริง | ไม่ตั้งระยะเวลาจากชื่อครึ่งวัน/เต็มวัน |
| schedule | เปิดพื้นที่/จองได้/ช่วงปิดตามตาราง | ไม่แทนสถานะสดหรือแอบรวมพักเที่ยง |
| closure | ข้อยกเว้นตามวันที่และขอบเขต | ไม่ยกวันหยุดชาติเป็นวันปิดศูนย์อัตโนมัติ |
| policy | ข้ออนุญาต/ห้าม เงื่อนไข ข้อยกเว้น ผลตามกฎ | ไม่เลือกนโยบายจากคนละภาษาเพื่อกลบ conflict |
| procedure | ขั้นตอน เอกสาร เงื่อนไขก่อนทำ | ไม่ใช้ deadline แทนวิธี หรือขั้นตอนแทน quota |
| competition | เกม รายการ ฉบับเอกสารและ metadata | ไม่เลือกฉบับคนละรายการด้วยชื่อเกมอย่างเดียว |
| competition_rule | ข้อกฎ เงื่อนไข ลำดับ/ข้ออ้างอิง | ไม่เอา fact card ที่ยังไม่ตรวจมาเป็นข้อกฎใหม่ |
| news | ข่าว กิจกรรม วันมีผล | ไม่มีข้อมูลจริงต้องไม่แต่งข่าวปัจจุบัน |
| person | ชื่อ บทบาท แหล่งข้อมูลและช่วงเวลา | ไม่รับรองบทบาทปัจจุบันจากข้อมูลเก่าที่ไม่ชัด |
| faq | คำถามภาษาคน คำตอบ topic/role/scope | ไม่ใช้รหัสภายในแทนชื่อแสดงหรือเลือกเรื่องใกล้เคียงผิด |
| live_binding | การเชื่อม service/resource กับระบบสด | ไม่มี mapping ต้องไม่สร้าง resource ID เอง |

## 4. รอบปรับแก้ที่เสนอ

### รอบ 1: แกนข้อมูลและความต้องการ

- ทำ S00–S06 และปรับคำอธิบายการวัดผล
- ใช้ F01–F07, F13–F15 และคู่ลบของตัวตน/หน่วยเป็นแกน
- เป้าหมาย: โครงสร้างของวิธีจ่าย/quota/identity พร้อมให้ candidate/planner ใช้และผ่านการตรวจส่วนประกอบ ยังไม่ปิดปัญหาคำตอบครบทั้งเส้นทางจนตรวจ S08/S10 ที่เกี่ยวข้องแล้ว

### รอบ 2: การค้นและแผน

- ทำ S07–S08 และตรวจส่วนประกอบคำตอบ S10
- ใช้ F04–F12, F27–F28 และ holdout คนละตระกูลคำถาม
- เป้าหมาย: target ที่ถูกต้องไม่หลุดเพราะคำเกริ่นและสำนวน โดยไม่ผ่อนให้ตอบเรื่องใกล้เคียงที่ไม่มีหลักฐาน

### รอบ 3: เวลา ภาษา การถามต่อ และข้อมูลแก้ใหม่

- ทำ S09–S12 และ regression ของสองรอบแรก
- ใช้ F13–F26 และ cases หมวดข้อมูลใหม่ในฐานแยก
- เป้าหมาย: เวลา/ราคา/ภาษา/state ถูก และเพิ่มข้อมูลโดยไม่เพิ่ม code branch ตามรายการ

### หลังแต่ละรอบ

- ใช้ S13 ตรวจสิ่งที่เปลี่ยน เก็บก่อน/หลังและข้อคงเหลือ แล้วปรับ Flow เมื่อหลักฐานชี้ว่าสาเหตุเดิมไม่ครบ
- ถ้ายังมีปัญหาที่ต้องแก้ ให้เปิดรอบถัดไปด้วยสมมติฐานและเกณฑ์ผ่านที่ชัดเจน ไม่วนทดสอบใหญ่โดยไม่มีจุดประสงค์
- เริ่ม S14 เมื่อผ่านขอบเขตที่ประกาศและมี facts ที่เจ้าของต้องรับรองครบตามการเผยแพร่นั้น

## 5. รายการคงค้างที่ไม่ควรซ่อนในคะแนน

- โมเดล/HTTP ยังถูกบล็อกสิทธิ์: เป็นอุปสรรคการรับรองจริง ไม่ใช่งานที่ทำเสร็จจากการเปิด flag
- ราคา/แพ็กเกจ/นโยบายที่ยังไม่มีวันมีผลหรือเงื่อนไขชัด: ไม่เติมเองเพื่อให้ test ผ่าน
- เอกสารต้นฉบับกติกาที่หายหรือปุ่มที่ยังไม่มีหลักฐาน: คง source gap และขอข้อมูลเฉพาะส่วน
- การตีความสำนวนใหม่ทุกแบบไม่มีหลักประกันจาก test จำกัด ต้องมี holdout และการเก็บเหตุผลของข้อผิดพลาดที่ตรวจต่อได้
