# แก้ขอบเขตการประเมิน: คำถามผู้ใช้ศูนย์เป็นหลัก

## การตัดสินใจจากคำชี้แจงผู้ใช้

ผู้ใช้ระบุว่าคำถามจริงควรอยู่ในเรื่องร้านเกม/ศูนย์ คำถาม DNS/TCP/TLS/HTTP 500 คำ และ RAM/SSD แบบบทความจึงแยกเป็น technical diagnostics ที่ผู้พัฒนาสร้าง ห้ามนับเป็นตัวแทนคำถามผู้ใช้หรือใช้เป็นเหตุให้เร่งพัฒนาบทความยาวก่อนงานบริการ

เอกสารนี้ปรับลำดับงานถัดไปของ FLOW.md และ RESULTS_ANALYSIS.md ผลเก่า/raw logs เก็บตามเดิม ข้อผิดพลาดด้าน source/target, เลข/หน่วย/คำปฏิเสธและ conversation context ยังเกี่ยวข้องกับบริการและคงมีประโยชน์ ไม่มีการเปลี่ยนการเปิด/ปิด general fallback ของ runtime ในการแก้ขอบเขตครั้งนี้

## Flow ที่ใช้ต่อ

1. เลือกคำถามจากบทสนทนาจริงและหมวดบริการ: ราคา/งบประมาณ/อุปกรณ์/เกม/กฎ/จอง/การมาถึง/ปัญหาหน้างาน
2. ผูก expected answer กับ owner source หรือผล booking fixture/live ที่มี timestamp ถ้าไม่มีข้อมูลให้ระบุว่ายังยืนยันไม่ได้ ไม่ใช้ LLM เดานโยบาย
3. ขยายสำนวน พิมพ์ผิด ถามกว้าง หลายเงื่อนไข และถามต่อด้วยคำสั้น โดยรักษา expected meaning เดิม
4. ตรวจความครบของส่วนที่ผู้ใช้ถาม: ถ้าขอทั้งหมดต้องครบ target scope; ถ้าเลือก PC หลังคำถามราคา ต้องสืบทอดราคาและกลุ่มผู้ใช้
5. ภาษาอังกฤษทดสอบความหมายเดียวกับภาษาไทย ราคา หน่วย ข้อยกเว้น และแหล่งข้อมูลต้องตรงกัน
6. ใช้หมวดเดียวกันวัดหลายคนพร้อมกัน: jobs/admission/เวลา/ความครบ/การปน session ไม่ใส่บทความความรู้ทั่วไปเป็น workload หลัก
7. เมื่อผิด ให้ไล่ trace ว่าผิดที่ input/context/routing/retrieval/coverage/rendering/live data แล้วแก้เฉพาะจุด ทดสอบเคสใกล้เคียงที่ถูกและผิดเพื่อกัน regression

## ชุดเคสบริการสำหรับรอบถัดไป — เตรียมแล้ว ยังไม่ได้รันในคำชี้แจงนี้

| หมวด | ตัวอย่าง | สิ่งที่ต้องตรวจ |
|---|---|---|
| ราคาและถามต่อ | ราคาบุคคลภายนอก → PC | รักษากลุ่มผู้ใช้และตอบแพ็กเกจ PC; บุคคลภายนอกอาจต้องแยกนักศึกษา/บุคคลทั่วไปตาม source |
| ราคาและทั้งหมด | ราคาบุคคลภายนอก → ทั้งหมด | ครบทุกบริการที่มี source และแยกกลุ่มราคา ไม่ fallback เป็น no_answer |
| งบประมาณ | เป็นบุคคลทั่วไป มี 100 บาท เล่น PC ได้กี่ชั่วโมง | คำนวณตามแพ็กเกจ/หน่วยจริง ไม่สมมุติแบ่งนาทีหรือโปรโมชัน |
| เหมาอุปกรณ์ | ขอราคาเหมาครึ่งวันกับเต็มวันทั้งหมด | ยึดตารางจากไฟล์เจ้าของ ระบุขอบเขตและเงื่อนไขครบ |
| จองกว้าง | บ่ายสามมีอะไรเล่นได้บ้าง | ระบุวัน/เวลาไทย และ list เฉพาะอุปกรณ์ที่ว่างจากข้อมูลสด ไม่ใช้ catalog แทน availability |
| จองหมวด | cockpit ว่างไหม | จำนวนว่าง/ทั้งหมด พร้อมรายเครื่องและ timestamp |
| พิมพ์ผิด | cockpik ว่างไหม | target ตรง Cockpit; ไม่แก้เวลา/เลขเครื่องโดยไม่มีหลักฐาน |
| VR | VR 9:00–9:30 ว่างไหม | ตรง policy ที่ผู้ใช้ยืนยันว่าจองกินช่วง9:00–10:00 |
| เกม | PC มีเกมอะไรบ้าง → ทั้งหมด | scope PC ต่อเนื่อง ไม่เปลี่ยนเป็นทุกโซนโดยไม่มีคำสั่ง |
| เล่นกับเพื่อน | มา4คนเลือกอะไรดี | ใช้ข้อมูล capacity/คำตอบเจ้าของ; ไม่เดากฎสลับคนเล่น |
| กฎ | กฏตอนเเข่ง cs2 มีอะไรมั่ง | rulebook CS2 ตาม source; ไม่ตอบเกมทั้งหมด/VALORANT/keyboard layout |
| กฎหลายส่วน | ขอทุกกฎของ Tekken 8 | ทุก section ที่มีหลักฐาน ไม่เลือกเฉพาะหัวข้อ/ไม่ปะปนเกม |
| กฎถามต่อ | กติกาแข่งมีอะไรบ้าง → ROV | รับชื่อเกมเป็น clarification answer และตอบส่วนที่ขอ |
| การจอง | walk in ได้ไหม ต้องจองไหม | ใช้ source เจ้าของว่าต้องจองผ่านระบบแม้ walk in |
| เช็กอิน | ต้องใช้บัตรอะไร | national ID/student/school/passport ตาม source ไทย–อังกฤษ |
| อุปกรณ์ส่วนตัว | เอาคีย์บอร์ดเมาส์ไปเองได้ไหม | รักษาคำปฏิเสธตามคำตอบเจ้าของ |
| ข้อมูลไม่พอ | เครื่องค้างระหว่างเล่นคืนเวลาให้ไหม | ไม่แต่งวิธีชดเชยหรือรับรองคืนเงินถ้า source ไม่มี |
| นอกขอบเขต | อธิบาย DNS 500 คำ | แยก out-of-domain ของการประเมิน; ยังไม่เปลี่ยน behavior runtime จนกำหนดนโยบาย fallback ชัด |

## ลำดับสำคัญที่ปรับ

P0 ข้อมูลศูนย์และกฎต้องตรง source → P0 ประวัติ/คำถามยืนยันรอบสอง/ขอทั้งหมด → P1 ความครบหลายหัวข้อและภาษาอังกฤษ → P1 availability สดและการจัดการ unavailable → P1 เวลาเมื่อหลายคนถามงานบริการพร้อมกัน → P2 ข้อความยาวเท่าที่เนื้อหาศูนย์จำเป็นจริง

คำขอ “กฎทั้งหมด” อาจยาวได้ เกณฑ์จึงเป็นครบทุกหัวข้อที่เกี่ยวข้องและอ่านได้ ไม่บังคับ 500 คำโดยไม่มีเหตุจากการใช้งานจริง ห้ามใช้ผล technical diagnostics เปลี่ยนความสำคัญงานบริการ
