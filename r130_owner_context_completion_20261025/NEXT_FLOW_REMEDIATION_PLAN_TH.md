# แผนแก้ Flow หลัง Full Test R130

สถานะ: แผนจากหลักฐานที่ตรวจแล้ว ยังไม่ได้อ้างว่าแก้หรือผ่านตรวจรับแล้ว

ขอบเขตเดิม R123 ทั้ง 76 หัวข้อและ 14 หมวดคงเดิม เอกสารนี้จัดลำดับงานที่ต้องทำต่อ ไม่ใช้แทนหรือลด REQUIREMENTS_TRACEABILITY.json และไม่เพิ่มคำถามใหม่ ไม่ฝึกหรือรัน baseline เดิมใหม่

เป้าหมายคือเข้าใจคำถามและบริบทครบ อ่านข้อมูลถูกขอบเขต ตอบทุกประเด็นที่มีหลักฐาน และแสดงข้อจำกัดตรงสาเหตุ ไม่ใช่เพียงเพิ่มคะแนน route, JSON หรือ keyword

## ลำดับที่ผู้ใช้ปรับล่าสุด — ทำข้อ02เป็นงานหลักก่อน

ผู้ใช้ให้ทำการวินิจฉัยข้อผิดพลาดก่อน งานข้อ02ต่อจากหลักฐานเดิม ไม่เริ่มจัดกลุ่มใหม่จากศูนย์ สถานะปัจจุบันอ่านผลครบ20,554requests/55,811grades จัดกลุ่ม9กลุ่มและ921reasonstringsแล้ว แต่การตรวจคำถาม/คำตอบ/โค้ด/sourceรายกรณีมี34requestsเท่านั้น โดยยืนยันcontent/scope/omissionfailure15ตัวอย่าง ยังไม่ใช่semantic adjudicationครบทุกคำถาม

สิ่งที่ต้องเติมก่อนเลือกวิธีแก้:

- ทำcase ledgerจากผลเดิม ระบุสิ่งที่ผู้ใช้ต้องการ คำตอบที่ได้รับ source/field/revision/locatorที่ควรใช้ และเงื่อนไขที่ตกหล่น
- ระบุจุดแรกที่ผิดในpipeline และแยกสาเหตุต้นทางจากอาการปลายทาง เช่นsourceมีแต่bindingผิด ไม่ลงสรุปเป็นdata_missing
- แยกconfirmed / probable / review_required พร้อมหลักฐานที่ยืนยันหรือยังขาด ห้ามขยายผล34casesเป็นคำตัดสินทุกcaseในกลุ่มเดียวกัน
- ผูกrootcauseกับเคสอื่นเฉพาะที่มีtrace/signatureที่ตรวจแล้วว่าสนับสนุนเหตุเดียวกัน เก็บจำนวนคำถามไม่ซ้ำแยกจากgrade occurrencesและกลุ่มซ้อนทับ
- ตรวจทั้งข้อที่graderบอกผิดแต่ความหมายอาจถูก และข้อที่ผ่านliteral/ledgerแต่คำตอบยังไม่ครบ จัดลำดับจากผลกระทบจริง จำนวนเคสที่ยืนยัน และความเสี่ยงในหมวดสำคัญ

ผลส่งมอบข้อ02: ทะเบียนปัญหาที่แยกcontent/protocol/source/transport/format/latency พร้อมระดับความมั่นใจ หลักฐาน ผลกระทบ และรายการที่ต้องตรวจต่อ จากนั้นจึงเลือกงานแก้ในข้อ03–17ตามสาเหตุ ไม่บังคับว่าต้องแก้protocolก่อนเสมอ ข้อ01เป็นการรักษาหลักฐานประกอบ และจะสร้างcandidateเมื่อเริ่มแก้runtimeจริง

## 01 — สร้าง candidate ถัดไปและตรึงหลักฐาน

- แยก runtime/data/prompt/backend ที่จะแก้จาก frozen R130 เก็บ raw ผลเดิม source เดิม approvals เดิม และ model assets เดิม
- ใช้คำถามและ grade identities เดิม บันทึก reference clock, locale, history, backend, profile, precision, timeout และ source snapshot
- ผูกทุกงานแก้กับ requirement เดิม กรณีผิดจริง และไฟล์ที่แก้ ไม่สร้างเปอร์เซ็นต์งานเสร็จจากจำนวนโมดูล

ผ่านเมื่อ: ตรวจย้อนหลังได้ว่าผลแต่ละรอบใช้ candidate ใด ไม่มีการเขียนทับผลเดิมหรือเปลี่ยน input ระหว่างวัด

## 02 — แยกคะแนนกับชนิดความผิดก่อนแก้

- เก็บ strict เดิมไว้ แต่แยก route/intent/mode, literal, outcome, source evidence, semantic coverage, latency และ transport
- ตรวจด้วย source ว่าคำตอบผิดข้อเท็จจริง ผิดขอบเขต ตอบไม่ครบ ถามกลับเหมาะสม หรือยังตัดสินไม่ได้
- เก็บ unknown/unassessed ในรายงานและตัวหารที่กำหนด ไม่ตัดทิ้งให้คะแนนดูสูง
- แยกชื่อ terminal provider_unavailable ที่รวมทั้ง model busy, timeout, schema failure และ live fixture ออกจากกัน

ผ่านเมื่อ: ปัญหา route หรือคำไม่ตรงไม่ถูกนับเป็น semantic wrong โดยอัตโนมัติ และคำตอบที่มี source แต่ผิดเรื่องไม่ถูกนับเป็น semantic correct

## 03 — แก้รูปแบบการสื่อสารกับโมเดล

- ทำ schema/version ของแต่ละ stage ให้แน่นอน: context planner, evidence selector และ general response
- ระบุ JSON/version ที่ต้องคืนใน prompt ตรงกับ parser และบังคับรูปแบบฝั่ง generation หาก backend รองรับ
- ถ้ายังไม่มี constrained decoding ต้องรายงานข้อจำกัด ไม่อ้างว่าการส่ง format schema เท่ากับบังคับ output แล้ว
- ตรวจ message/schema/profile/adapter/stage จริง ไม่ยอมรับ input echo ว่าเป็นผลเลือกหลักฐาน
- ทำ compatibility adapter เฉพาะรูปแบบเก่าที่แปลงได้โดยไม่เดาหรือทำความหมายหาย

ผ่านเมื่อ: ผลตอบกลับที่ถูกโครงสร้างถูกใช้ต่อได้ และผลผิด schema ถูกจัดเหตุถูกต้องโดยไม่กลายเป็นคำตอบทางธุรกิจที่แต่งขึ้น การผ่าน JSON ยังไม่ปิดเกณฑ์ semantic

## 04 — ทำแผนความเข้าใจคำถามชุดเดียวให้ทุกขั้นใช้ร่วมกัน

- เก็บทุกสิ่งที่ถาม: ประเด็นหลัก ประเด็นย่อย เป้าหมาย การกระทำ ผู้กระทำ เงื่อนไข คำปฏิเสธ เวลา กลุ่มผู้ใช้ จำนวน และขอบเขตรายการแข่งขัน
- แยก factual need จากคำสั่งรูปแบบ เช่น “ตอบสั้น” และ “ตอบเฉพาะประเด็นนี้”
- ไม่ให้ native shortcut/router/fallback เปลี่ยนเจตนาที่ตรวจแล้วโดยไม่มีเหตุผลและหลักฐาน
- เส้นทางเร็วใช้ได้เมื่อพิสูจน์ว่าเข้าใจขอบเขตครบ หากยังคลุมเครือต้องเข้าการตีความ ไม่เร่งตอบจาก keyword เดียว

ผ่านเมื่อ: คำถามหลายส่วนมีรายการสิ่งที่ต้องตอบครบก่อนค้นข้อมูล ไม่ใช้จำนวน tasks ที่ planner สร้างเองเป็นหลักฐานว่าครบคำถามแล้ว

## 05 — แก้การผูก entity และระดับความเฉพาะเจาะจง

- เกม → บริการ → โซน → เครื่อง ต้องเชื่อมตาม relation ที่มีจริง
- แยกชื่อเกม รุ่นเกม ชื่อบริการ รุ่นอุปกรณ์ และทรัพยากรรายเครื่อง
- PC #10 ต้องคงหมายเลขถึงการอ่านและการตอบ ไม่ลดเป็น PC Zone
- ตรวจ candidate pool ว่ามี field ที่ถามจริง ไม่ให้ pool ที่มีชื่อคล้ายแต่ผิดชนิดกีดกัน candidate ที่ถูกต้อง
- แก้ GPU ที่มีใน equipment_gaming_pc.specifications แต่ถูกตอบว่าไม่มีข้อมูล

ผ่านเมื่อ: คำตอบเฉพาะเครื่องใช้หลักฐานระดับเครื่อง หรือบอกตรง ๆ ว่ายังไม่ยืนยันเครื่องนั้น ไม่อ้างระดับโซนแทน

## 06 — แก้บริบทและคำอ้างกลับ

- เชื่อม “it/เครื่องเดิม/เกมนั้น” กับเป้าหมายที่มี provenance จากข้อความปัจจุบันหรือประวัติที่ระบบรับรอง
- หลัง resolve ได้ต้องล้าง ambiguity เฉพาะส่วนที่คลายแล้ว และส่ง binding ถึง executor ไม่ถามชื่อเกมซ้ำ
- เก็บขอบเขตร่วม เช่น กลุ่มผู้ใช้ วันที่ และรายการแข่งขัน ไปยังคำถามย่อยที่อยู่ภายใต้ขอบเขตนั้น
- ถ้าเปลี่ยนเรื่องหรือมี override ต้องหยุดสืบทอดเฉพาะส่วนที่เปลี่ยน
- ถ้ามีหลาย antecedents ที่ทำให้คำตอบต่างกันจึงถามกลับ ไม่เลือกตัวท้ายโดยอัตโนมัติ

ผ่านเมื่อ: เคส Tekken8→it ใช้ชื่อเกมที่ผูกแล้ว และเคสการแข่งขัน→อาหารยังใช้กติกาการแข่งขัน เว้นแต่ผู้ใช้เปลี่ยนขอบเขตจริง

## 07 — แยกความหมายของคำถามที่หน้าตาคล้ายกัน

- เกมที่ศูนย์มี ≠ เครื่องว่าง ณเวลาใด
- จำนวนผู้เล่นในทีม ≠ จำนวนคนช่วง Match Prep ≠ จำนวนคนที่เกมรองรับ
- ดูสตรีม ≠ ถ่ายทอดสตรีม
- ลูกค้ายกเลิกจอง ≠ ศูนย์ยกเลิกเพราะผิดเงื่อนไข
- เช่าอุปกรณ์กลับบ้าน ≠ เหมาโซนใช้ในศูนย์
- members of the public ≠ รายชื่อสมาชิก/บุคลากร
- ราคาซื้อเกม ≠ ค่าใช้บริการเล่นเกมที่ศูนย์

ผ่านเมื่อ: เลือก operation จาก predicate และบริบท ไม่ใช้คำที่ซ้ำกันเป็นเหตุเลือกหมวดเพียงอย่างเดียว

## 08 — ทำบัญชีความครบของคำตอบก่อนและหลังอ่านข้อมูล

- ตั้งรายการสิ่งที่ต้องตอบจากคำถามก่อนเลือก source
- ผูก source/field/claim กับแต่ละประเด็น ไม่ให้ clause เดียวปิดคำถามหลายส่วนที่ยังไม่ตอบ
- เปรียบเทียบหลายตัวเลือกต้องอ่านครบทุกตัวเลือก ไม่รวมราคา alternatives เป็นยอดซื้อรวม
- งานอิสระยังตอบได้แม้อีกส่วนต้องถามเพิ่มหรือ provider ไม่พร้อม
- ตรวจ coverage จากคำถามต้นฉบับอีกครั้ง ไม่ตรวจเฉพาะ tasks ที่รอดมาถึงท้าย pipeline

ผ่านเมื่อ: ทุกประเด็นมีคำตอบที่อ้างหลักฐานได้ หรือมีสถานะขาด/คลุมเครือ/ขัดกัน/ไม่รองรับที่ตรงสาเหตุ

## 09 — แก้กติกาแข่งขันและโครงสร้างเอกสารเป็นงานสำคัญ

- เก็บ game/event/edition/year และ section hierarchy ให้ครบ
- แยก document title, section heading, substantive rule, condition, exception และ penalty
- แก้กรณี text เท่ากับ heading แต่เป็นประโยคกติกาเต็ม จึงถูก substantive guard ปฏิเสธผิด
- แก้กรณีชื่อเอกสาร Tekken8 ถูกใช้เป็นคำตอบ competition format ทั้งที่ไม่มี FT2/R3/60S
- ตรวจ metadata เช่น CS2 settings045 ที่ถูกจัด facet ผิด และอ่าน clause ที่เกี่ยวข้องข้าม section ให้ครบ
- ห้ามกฎศูนย์ทั่วไปทับกติกาการแข่งขันเพราะคำถามย่อยละชื่อรายการ

ผ่านเมื่อ: คำถาม settings+macro ตอบทั้งสองส่วน และการแข่งขันมีข้อห้าม/ข้อยกเว้น/บทลงโทษตรงรายการ ไม่ใช้แค่ source ID หรือคำว่า format เป็นเกณฑ์ครบ

## 10 — แก้ verifier ให้ตรวจความหมายของสิ่งที่ตอบ

- ตรวจแยกว่าหลักฐานมีจริง และว่าหลักฐานนั้นตอบ predicate/actor/target/conditions ที่ถามจริง
- ตรวจทั้ง false rejection ที่ตัดคำตอบถูก และ false acceptance ที่ปล่อยคำตอบไม่ครบ
- ห้าม supported/all_obligations_fulfilled ของแผนบางส่วนถูกอ้างเป็น whole-question correctness
- ถ้า verifier ไม่รู้ให้คง review_required ไม่บังคับทุกกรณีเป็นผ่าน/ไม่ผ่านด้วย heuristic เปราะบาง

ผ่านเมื่อ: CS2 clause เต็มไม่ถูกตัดเพราะเท่ากับหัวข้อ และชื่อเอกสารอย่างเดียวไม่ผ่านการตอบรูปแบบการแข่งขัน

## 11 — แก้ source authority, การย้ายข้อมูล และ validity

- แยก source ไม่มีจริง, relation ขาด, metadata ผิด, reader หาไม่เจอ, source ถอนแล้ว และ validity ไม่ยืนยัน
- ตรวจค่าฟิลด์กับ source body/locator/revision ไม่ยืนยันจาก status=known อย่างเดียว
- รวมแหล่งที่เงื่อนไขตรงกันได้เมื่อเทียบ actor/action/condition/exception ครบ พร้อมรักษา provenance
- เมื่อข้อกำหนดต่างจริงต้องแสดง conflict ไม่เลือกจาก timestamp หรือ trust อย่างเดียว
- กำหนด effective interval ของราคา/นโยบายโดยหลักฐาน ไม่เอาวันยืนยันล่าสุดมาเป็นวันเริ่มใช้โดยอัตโนมัติ
- เจ้าของเพิ่ม/แก้/ถอนข้อมูลแล้วคำถามถัดไปต้องใช้ snapshot ใหม่โดยไม่ฝึก weights เพื่อใส่ business facts
- เก็บ draft/published/approval ตามกระบวนการเดิม

ผ่านเมื่อ: ไม่ขอเจ้าของกรอกข้อมูลที่มีแล้วซ้ำ และไม่ใช้ข้อมูลเก่าหรือที่ถอนแล้วเพียงเพื่อให้มีคำตอบ

## 12 — แก้ราคาและการคำนวณ

- บังคับ service, audience, คนเล่น, ขนาดกลุ่ม, ระยะเวลารวม, ระยะเวลาต่อรอบ และ billing rule ให้ถูกบทบาท
- แสดงว่าตัวเลขใดเป็นราคาต่อคน/ต่อเครื่อง/ต่อกลุ่ม/ต่อรอบ
- คิด 30 นาทีหรือเกินรอบได้เฉพาะเมื่อมีกฎ proportional/round-up/minimum charge ยืนยัน
- แยก rate หลายขนาดกลุ่มให้มี label และถามเพิ่มเมื่อข้อมูลนั้นทำให้ยอดต่างจริง
- คำนวณด้วยโค้ดและตรวจย้อนกลับจาก source operands ไม่ให้ LLM คิดจำนวนเงินเอง

ผ่านเมื่อ: จำนวนเงินมี operand/unit/rule/effective-source ที่ตรวจซ้ำได้ และไม่มีการเลือก audience หรือขนาดกลุ่มเองจากคำกว้าง ๆ

## 13 — แก้วันเวลาและ live binding

- ใช้ trusted Bangkok clock และ reference date ของคำขอ
- รักษากติกาวันที่อย่างเดียวที่ผู้ใช้สั่ง: วันยังไม่ผ่านให้ใช้เดือนเดียวกัน; วันผ่านแล้วถามเดือนก่อน และรับคำตอบต่อในประวัติได้
- แยกเวลาอาคารเปิด เวลาให้เล่น ช่วงจอง ช่วงบำรุงรักษา วันปิดพิเศษ และเครื่องว่างจริง
- เรียก provider เมื่อคำถามต้องใช้ข้อมูลสด พร้อม exact resource/date/time/window, identity, timezone, TTL และ slot coverage
- unavailable/stale ไม่แปลว่า free, occupied หรือ closed
- static catalog ต้องไม่ถูกส่งไป live เพราะคำว่า available เพียงคำเดียว
- ผล controlled unavailable ทดสอบเฉพาะพฤติกรรมเมื่อ provider ไม่พร้อม ไม่ใช่ข้อสรุปสถานะ provider จริง

ผ่านเมื่อ: คำถามวัน/เวลาคืนคำตอบตรงชนิดข้อมูล และการอ้าง live มีหลักฐานครบช่วงที่ถาม

## 14 — แก้คิว งบโมเดล timeout และ latency

- local read ที่เข้าใจขอบเขตแน่นอนแล้วไม่ควรรอ context model เช่น building/floor
- ผูก concurrency/admission กับ queue และ request deadline ไม่ปฏิเสธทันทีจนงานที่ตอบได้กลายเป็น retry
- กันการ retry ซ้ำหลายชั้น และแยก stage ที่จำเป็นจาก stage ที่ควรใช้ code
- คำนวณ budget จาก request รวม เพื่อไม่ให้งานแรกกินสิทธิ์ของงานถัดไป
- วัด end-to-end latency และเวลารอ/สร้างคำตอบ/parse/อ่านข้อมูล/fallback แยกกัน
- ตรวจ p95/p99/จำนวนเกิน20วินาที ไม่ใช้ median เร็วกลบ tail ช้า

ผ่านเมื่อ: ลด unnecessary model calls และ tail บนชุดเดิม โดยไม่ลดคุณภาพหรือปิด LLM เพื่อทำให้เวลาและคะแนนดูดี

## 15 — จัดคำตอบให้ตอบตรงและอ่านง่าย

- เปิดด้วยคำตอบคำถามนั้น ไม่เปิดด้วยชื่อเอกสารยาวหรือคำเตือนทั่วไป
- ใช้ขั้นตอนสำหรับวิธีจอง ตารางสำหรับเปรียบเทียบ รายการสำหรับเกม และคำตอบสั้นสำหรับข้อเท็จจริงหนึ่งข้อ
- แสดงเงื่อนไขที่เปลี่ยนผล เช่น กลุ่มราคา หมายเลขเครื่อง รายการแข่งขัน และข้อยกเว้นใกล้คำตอบ
- ถ้าตอบได้บางส่วนให้บอกว่าส่วนไหนตอบแล้ว ส่วนไหนยังไม่ยืนยัน
- ภาษาไทย/อังกฤษ/auto ใช้ requested locale และแยก proper name ภาษาไทยจาก prose ที่ผิดภาษา
- ไม่แสดง internal field names, budget codes หรือบันทึกการแก้ข้อมูลแทนคำตอบผู้ใช้

ผ่านเมื่อ: รูปแบบอ่านเข้าใจได้จากคำตอบเดียว และไม่ลด/เปลี่ยนเงื่อนไขของ source เพื่อให้ข้อความลื่น

## 16 — ใช้ Flow เดิมเป็นหลักฐานสำหรับ distillation อย่างถูกต้อง

- เทียบคำถาม key เดียวกันกับคำตอบและ trace ที่บันทึกไว้ของ Flow เดิม
- ระบุว่าเดิมดึง source ใด เลือก field/operation ใด ผูกบริบทอะไร และรูปแบบคำตอบเป็นอย่างไร จาก log ที่มีจริง
- ถ้าไม่มี trace ให้ระบุว่าไม่ทราบ ไม่เดา reasoning ภายในโมเดล
- ตรวจคำตอบครูกับ source รุ่นที่ตรงกันก่อนใช้เป็น label
- สอน planner เรื่อง task/target/slot/action/scope/binding/clarification ไม่ยัดราคา/เวลา/นโยบายที่เปลี่ยนได้ลง weights
- แบ่ง family ข้าม train/eval ให้ถูก และไม่เรียกชุดที่เคยเห็นว่า fresh holdout

ผ่านเมื่อ: label แต่ละรายการชี้ source/input/เหตุผลตรวจรับได้ ไม่เลียนแบบคำตอบเก่าที่ผิดหรือข้อมูลเก่า และไม่ฝึกซ้ำก่อนแก้ integration ที่ทำให้แผนถูกแต่ตอบผิด

## 17 — ตัดสินเรื่องโมเดลหลังแก้การเชื่อมต่อ

- ตรวจ Typhoon retained/base บน prompt/schema/backend ที่เข้ากันได้ก่อนประเมินความสามารถ
- การเปลี่ยนโมเดล ฝึก LoRA หรือปรับ prompt ต้องเป็นการทดลองคนละตัวแปรที่ระบุชัด
- ประเมินทั้ง schema, intent, operation, target, slots, shared scope และคำตอบที่อ่านจาก source จริง
- ตัวใหม่ต้องดีขึ้นและไม่ถอยในหมวดสำคัญ ไม่มีการ promote จาก JSON ดีขึ้นอย่างเดียว
- ถ้าทดสอบรุ่นอื่นต้องพิจารณาคุณภาพ ภาษาไทย หน่วยความจำ เวลา และเงื่อนไข backend จริง โดยยังไม่สรุปจากขนาดพารามิเตอร์เพียงอย่างเดียว

ผ่านเมื่อ: มีผล paired comparison ภายใต้ engine/data/clock/budget เดียวกัน และ critical source review ผ่านก่อนเลือกน้ำหนัก

## 19 — ลำดับการทดสอบที่ไม่สิ้นเปลืองหรือกลบ regression

1. ใช้เคสผิดที่ยืนยันแล้วจาก R130 ตรวจ defect ที่แก้ พร้อมเคสเดิมที่เสี่ยงถอยจากจุดเดียวกัน
2. ใช้ชุดเดิมรายหมวดและ paired planner cases โดยคง inputs/source/clock ให้ตรงกัน
3. ตรวจ multi-turn, หลายประเด็น, owner50, add/edit/withdraw และ provider failure ด้วยชุดที่มีอยู่แล้ว
4. ตรวจ source/operation/coverage จริง และดูกรณีที่ตอบถูกแต่ format ต่างด้วย
5. เมื่อ candidate ผ่าน gates ที่กำหนดจึง Full Test อีกครั้ง ไม่รัน Full หลังแก้จุดเล็กทุกครั้ง
6. เทียบ saved legacy/R95 ด้วย identities เดิมและรายงาน confounds ไม่รันหรือ regrade baseline เดิมใหม่

ผ่านเมื่อ: confirmed defects ที่อยู่ในชุดรับถูกแก้ เคสสำคัญเดิมไม่ถอย และไม่มีการเปลี่ยนคำถาม/ตัวหาร/เกณฑ์หลังเห็นผลเพื่อให้คะแนนดีขึ้น

## 20 — เงื่อนไขการปิดงาน

- อัปเดต76requirementsด้วย code/source/test/semantic evidence รายข้อ คงรายการที่ยังไม่ผ่านไว้
- ปิด source-confirmed critical defects ของ candidate และตรวจผลข้างเคียงที่เกี่ยวข้อง
- มีผล paired comparison ที่อธิบายได้และไม่ถอยใน critical domains
- Full coverage ครบ20,554keys/55,811grade identities ไม่มีขาดหรือซ้ำ และ source/input/weights/model provenance ไม่เปลี่ยนระหว่างวัด
- รายงาน strict/literal/semantic review/unknown/transport/latency แยกกัน พร้อมข้อจำกัดและสิ่งยังไม่ยืนยัน
- การติดตั้งจริงเป็นขั้นแยก ไม่ติดตั้งทับ R78 เพียงเพราะ test หรือ API readiness ผ่าน

ไม่ใช้คำว่า “ครบ100%” จากจำนวนฟังก์ชัน การผ่าน JSON หรือ keyword checks และไม่ตั้งเป้าความแม่นยำ99%ลอย ๆ โดยยังไม่มีชุดตรวจและหลักฐานที่รองรับ
