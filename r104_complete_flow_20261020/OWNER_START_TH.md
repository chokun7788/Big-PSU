# ใช้และเพิ่มข้อมูลใน candidate R103

รุ่นนี้อยู่ในโฟลเดอร์ทดลองแยก ใช้ runtime protocol/build identifier บางส่วนของ R102 เพื่อรักษาความเข้ากันได้ ให้ดู source manifest และรายงานทดสอบ R103 ประกอบ ยังไม่ติดตั้งทับแชท production

## เปิดใช้งานในเครื่องนี้

1. เปิด Ollama ให้พร้อมและมีโมเดล `scb10x/typhoon2.5-qwen3-4b` ตาม MODEL_CONFIG_MANIFEST.json
2. เปิด `Open-Preview.cmd` เพื่อดูข้อมูลที่ย้ายมาในแชททดลอง พอร์ตเริ่มต้น 8131
3. เปิด `Open-Owner.cmd` เพื่อเพิ่ม/แก้ข้อมูล พอร์ตเริ่มต้น 8132
4. `Open-Published.cmd` อ่านเฉพาะข้อมูลที่อนุมัติและเผยแพร่แล้ว ฐานข้อมูลจริงที่สำเนามายังไม่มี active publication จึงต้องไม่คาดว่าร่างจะโผล่ในโหมดนี้

ตัวเปิดยังเรียก Start-R102.ps1 ที่อยู่ในโฟลเดอร์ candidate นี้จริง ชื่อไฟล์เป็น compatibility launcher ไม่ได้ชี้ไปใช้โฟลเดอร์ R102 เดิม ต้องเก็บ candidate ไว้ภายใน project ที่มี bundled Python; ชุดนี้ยังไม่ใช่ portable bundle ที่รวมโมเดลสำหรับส่งเครื่องอื่น

## เพิ่มข้อมูลปกติ

1. เลือกหมวด → สร้างใหม่
2. ตั้งชื่อที่คนเข้าใจได้ รหัสรายการใช้เชื่อมความสัมพันธ์และควรคงเดิมเมื่อแก้ข้อมูลเดิม
3. ช่องที่มีข้อมูลต้นทางให้เลือก “มีข้อมูลยืนยัน” และกรอกตามตัวอย่าง ช่องที่ไม่มีหลักฐานคง “ไม่ทราบ” ไม่ใส่ 0/ไม่มี เพื่อให้ผ่านฟอร์ม
4. เลือกรายการที่อ้างถึง เช่น game_service ต้องเลือกเกมกับบริการที่สร้างไว้แล้ว
5. ระบุวันเริ่มใช้/สิ้นสุดเฉพาะที่ยืนยันได้ โดยเฉพาะราคาและตารางเวลา
6. กรอก/แปลภาษาอังกฤษ แล้วตรวจเงื่อนไข ตัวเลข คำห้าม และข้อยกเว้นก่อนเปลี่ยนสถานะว่า reviewed
7. บันทึกร่าง → ดูคำเตือน readiness → preview คำถามเฉพาะเนื้อหาที่ใส่
8. ตรวจ diff กับฉบับเดิม → อนุมัติ → เผยแพร่ จึงมีผลใน Published chat ไม่ต้องเพิ่ม if/else ต่อชื่อเกมในโค้ด

## ตัวอย่างเกมใหม่

ตัวอย่างสมมุติ ไม่ใช่ข้อมูลศูนย์จริง:

- game: ชื่อ Aurora Demo; ภาพรวม; วิธีเล่น; แพลตฟอร์ม
- game_service: เลือก Aurora Demo + บริการ PC ที่มีอยู่; offered=true เมื่อศูนย์ยืนยันว่ามีให้บริการจริง
- game_mode: เลือก Aurora Demo; โหมด; platform; players_min/players_max
- control_set: เลือก Aurora Demo; platform; ปุ่ม/การกระทำ; ข้อจำกัด/เวอร์ชัน

ชื่อเกม/วิธีเล่นใน game ไม่ยืนยันว่าศูนย์ติดตั้งแล้ว ต้องมี game_service การรองรับแพลตฟอร์มไม่ใช่หลักฐานการให้บริการจริง

## เปลี่ยนราคาเดิม

เปิดรายการ rate เดิม → กรอกจำนวนบาท ไม่ต้องคูณ 100 เอง → ตรวจ service/audience/unit/duration/calculation_rule และวันมีผล → บันทึกและตรวจ diff → อนุมัติ/เผยแพร่

หากเพิ่มเป็น rate อีกฉบับที่มีขอบเขตและช่วงเวลาซ้อนกันแต่จำนวนต่างกัน ระบบควรบล็อก conflict จนแก้ ไม่เลือกตัวเลขใหม่เพียงเพราะแก้ล่าสุด

หากใส่ FAQ บอกว่าราคาเปลี่ยนและทำ advanced supersession แล้ว แต่ยังไม่แก้ typed rate ระบบจะหยุดคำนวณจากอัตราเก่า ไม่เอา prose ไปเปลี่ยน approved rate โดยเงียบ ๆ

## กติกาการแข่งขัน

สร้าง competition ที่เลือก game, event, division, rulebook release และช่วงที่ใช้ จากนั้นสร้าง competition_rule แยกตามข้อจริง:

- heading/text เก็บเงื่อนไขและข้อยกเว้นครบทั้งย่อหน้า
- competition_id ต้องตรงรายการนั้น
- depends_on_ids เลือกข้อที่ต้องอ่านร่วม ภายในรายการเดียวกัน
- completeness=complete ใช้เมื่อข้อความครบจริง หากข้อความถูกตัดต้องคง incomplete และไม่ยืนยันเป็นกฎเต็ม

เกมเดียวมีหลายรายการ/รุ่น ระบบอาจถามให้เลือกรายการก่อน การตอบด้วยชื่อหลังถามต้องคง topic เดิม ไม่เริ่มอธิบายภาพรวมเกมใหม่

## Advanced claim mapping ใช้เมื่อใด

ใช้เชื่อมข้อเท็จจริงข้ามหมวดที่ฟอร์มปกติ/ความสัมพันธ์มาตรฐานยังอธิบายไม่ได้ ไม่จำเป็นสำหรับการเพิ่มเกม/บริการ/ราคา/ข้อกติกาปกติ

- บันทึกรายการที่อ้างถึงก่อน แล้วเลือก subject/value record/field
- ID ของ mapping สร้างให้ครั้งเดียว หน่วยเลือก canonical unit ให้ตรงตารางราคา
- ระบุ actor/applicability/conditions/exceptions ตามต้นทาง ไม่กด known ทั้งหมดโดยไม่มีหลักฐาน
- supersedes ต้องมีหลักฐานยืนยันอำนาจและขอบเขตการแทนที่โดยเฉพาะ
- คำถามอาจยังต้องตีความหรือถามกลับ แม้ schema ผ่าน ไม่ใช่การรับรองทุก paraphrase อัตโนมัติ
