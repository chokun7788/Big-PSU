# ทำอย่างไรให้ Flow กลางตอบได้เทียบเท่าหรือดีกว่า Legacy

## 1. คำตอบสั้น

ต้องย้าย **ความสามารถในการแปลงคำถามเป็นงานและเลือกหลักฐาน** มาทำงานบนฐานกลาง ไม่ใช่ย้ายแต่ข้อมูล แล้วให้ field matcher หรือ LLM เลือก record เพียงครั้งเดียว

แนวทางหลักที่เสนอคือ:

1. ใช้ตัวตีความเฉพาะหมวดของ Legacy ที่พิสูจน์แล้ว เป็นผู้เสนอแผนงาน โดยไม่อนุญาตให้นำ facts/คำตอบเก่ามาตอบแทนฐานกลาง
2. ทำ task contract ที่บอกความหมาย ช่องที่ต้องรู้จริง relation ที่ต้องตาม และข้อยกเว้น
3. ให้ LLM ช่วยแปลงคำถามที่หลากหลายเป็นแผนจำกัดขอบเขต พร้อมข้อมูล schema และตัวอย่างระดับงาน
4. ตรวจว่าหลักฐานพอตอบแต่ละส่วนหรือไม่ แทนการยกเลิกคำตอบทั้งหมดเมื่อมีคำบางคำยังจับไม่ได้
5. อ่านและคำนวณจากข้อมูลกลางที่มีผล แล้วจัดคำตอบให้ตรงงาน
6. วัดความครบ ความถูกต้อง การถามกลับเกินจำเป็น และการเดาโดยไม่มีหลักฐาน แยกจากคะแนนคำตรงและ transport

ทั้งหมดเป็นข้อเสนอทางวิศวกรรมจากหลักฐานด้านล่าง ยังไม่มีผลทดสอบหลังเปลี่ยนตามแผนนี้

## 5. หลักฐานจากโค้ดและคำตอบจริง

### D01 — task selector รุ่นใหม่ยังเป็น single task / single candidate

`task_proposer.py:31` สั่งให้เลือกงานเดียวและ candidate เดียว ขณะคำถามจริงอาจขอทั้งราคา วิธีจอง และเอกสาร การยอมรับ JSON ที่ถูกชนิดยังไม่พิสูจน์ว่าคำถามทุกส่วนถูกเก็บไว้

**ข้อเสนอ:** เปลี่ยน representation เป็นรายการ needs ที่มี subject/qualifier ของตัวเอง แล้ว compile เป็นแผนอ่านหลายส่วนที่มีขอบเขต ไม่แยกที่คำว่า and/และทุกครั้ง เพราะบางคำเป็นชื่อข้อกฎหรือชื่อเรื่องเดียวกัน

### D02 — เงื่อนไขที่สำคัญถูกใช้เป็นเหตุส่งกลับ compatibility กว้างมาก

`task_flow.py:117–120` มีตัวเลข คำปฏิเสธ and/or อายุ เงื่อนไขการจ่าย และความเป็นเจ้าของเป็นเหตุหลีกเลี่ยง semantic task path ความตั้งใจป้องกันการเดามีเหตุผล แต่ทำให้คำถามใช้จริงจำนวนมากยังไม่ใช้ความสามารถใหม่

**ข้อเสนอ:** เก็บสิ่งเหล่านี้เป็น typed slots/qualifiers ที่ห้ามหาย แล้วส่งไป domain executor ที่ตรวจได้ ไม่เอาคำเงื่อนไขออกเพื่อให้ผ่านง่ายขึ้น

### D03 — source field เป็นรายการแบน แต่ความหมายของงานเป็น relation และทางเลือก

`task_contracts.py:17` ประกาศ game_players ด้วย players_min, players_max, mode_name, studio_supported; validator ที่ `answer.py:1037–1040` ตรวจผลอ่านตาม requested_fields

ใน log “VALORANT ใช้ผู้เล่นกี่คน” อ่าน game_detail_valorant แล้วขาดสี่ fields จึงถูกปฏิเสธ ไม่ใช่หลักฐานว่าข้อมูลทุกชนิดเกี่ยวกับจำนวนคนไม่มีอยู่ในฐาน ต้องตรวจ relation game→game_mode และแยกจำนวนคนในเกมจากจำนวนผู้เข้าพื้นที่เตรียมแข่ง

**ข้อเสนอ:** required claims ตามคำถาม, optional context และ `any_of` เส้นทางอ่าน ต้องแยกกัน หากตรวจ source แล้วไม่พบจริง ให้บอกส่วนที่ไม่มี ไม่เติมจำนวนจากความจำของโมเดล

### D04 — การตรวจข้อความเหลืออยู่ทำให้ทิ้งข้อมูลที่พบแล้ว

ตัวอย่าง “ตอนเย็นเปิดถึงกี่โมง” เจอ FAQ ตารางบริการ แต่ “ตอนเย็น” ค้างใน unresolved clauses; คำถาม refund เจอ FAQ ถูกเรื่อง แต่ส่วน “Please tell me: can I get a” ค้างอยู่เช่นกัน ที่ dispatcher `migrated_chat.py:106` ตรวจและอาจลงท้ายด้วยคำถามกลับทั่วไป

**ข้อเสนอ:** แยกข้อความประกอบการพูดออกจากเงื่อนไขที่เปลี่ยนคำตอบ พร้อม raw span map; เงื่อนไขช่วงเวลาต้องมี temporal interpretation หรือคำตอบขอบเขตที่อ้างอิงได้ ไม่บอกว่าเป็น filler

### D05 — เรื่องกติกาอาจไปอ่านข้อมูลเกม

“ROV ถ้าเกมหลุดทำยังไง” ใน log เลือก migrated_game_arena_of_valor_rov และ field steps จึงขาด field แทนที่จะตรวจข้อกติกา/ขั้นตอนที่เกี่ยวข้อง

**ข้อเสนอ:** จับ operation ก่อน type ของ field; “ทำยังไง” ไม่เท่ากับ procedure.steps ทุกกรณี ผูก game/event/edition และเรื่องย่อย แล้วค้น rule clauses หากยังไม่ชัดว่าแข่งหรือเล่นทั่วไป ให้ถามเฉพาะบริบทนั้น

### D06 — ประวัติสั้นยังมี shortcut กลับ compatibility

`task_flow.py:185` ส่งคำตอบสั้นที่มี history กลับเส้นทางเดิมเป็นส่วนหนึ่งของการป้องกัน scope ปะปน ยังต้องพิสูจน์ต่อว่า state ของ “ทั้งหมด”, “PC”, “บุคคลภายนอก” สืบทอด task และ slot ถูก

**ข้อเสนอ:** pending slot state ที่เชื่อถือได้จากสิ่งที่ส่งจริง + ตรวจ revision ปัจจุบัน แยกจากข้อความคำตอบเก่า ทั้งนี้ full R95 เป็น single-turn จึงยังไม่มีหลักฐานสถิติว่าการสนทนาหลายรอบผ่านในวงกว้าง

## 6. งานวิจัยที่นำมาใช้และขอบเขตการอนุมาน

ส่วนต่อไปเป็นสรุปงานวิจัยสั้น ๆ ส่วน Flow ในไฟล์ถัดไปเป็นการออกแบบของโครงการนี้ ไม่ใช่การอ้างว่าบทความเสนอ implementation เดียวกัน

### P01 — Description-Driven Task-Oriented Dialog Modeling (D3ST), 2022

งานเสนอให้ใช้คำอธิบายความหมายของ intents/slots แทนการพึ่งชื่อย่อ และทดสอบการย้ายไปงานที่ไม่เคยเห็น โมเดลของงานมีการฝึก ไม่ใช่หลักฐานว่าการเขียน prompt อย่างเดียวจะทำให้ Typhoon 4B ได้ผลเดียวกัน

**นำมาใช้:** task cards อธิบายว่า game players, device capacity, competition roster ต่างกันอย่างไร พร้อมชนิดค่าและแหล่งอ่าน เลือก ID จากชุดที่อนุญาต

[บทความและวิธีการ](https://arxiv.org/html/2201.08904v1)

### P02 — Show, Don’t Tell, NAACL 2022

งานใช้ตัวอย่างบทสนทนาที่ติดป้าย state เพื่อแสดงความหมายของ schema และประเมิน zero-shot state tracking ให้เหตุผลสนับสนุนการเพิ่ม demonstrations ร่วมกับคำอธิบาย ไม่ได้พิสูจน์ว่า generic schema จะรับคำถามทุกแบบโดยไม่พัฒนาเพิ่ม

**นำมาใช้:** ตัวอย่างระดับ task family เช่น price→ถาม service→PC ไม่ต้องให้เจ้าของเขียน alias และคำตอบหลายสิบแบบสำหรับเกมใหม่ทุกเกม

[บทความ](https://aclanthology.org/2022.naacl-main.336/)

### P03 — RAT-SQL, ACL 2020

งานมุ่งแก้ schema linking และการแทนความสัมพันธ์ในฐานข้อมูลที่ไม่เคยเห็น สนับสนุนว่าการรู้ชื่อ column อย่างเดียวไม่พอ ต้องเชื่อมคำถามกับโครงสร้างและ relations

**นำมาใช้:** task read graph สำหรับ game→mode, zone→service→resource, service→rate→audience; ไม่จำเป็นต้องย้ายระบบไปใช้ RAT-SQL หรือเปิดให้ LLM เขียน SQL อิสระ

[บทความ](https://aclanthology.org/2020.acl-main.677/)

### P04 — PICARD, EMNLP 2021

งานจำกัด token ระหว่างสร้าง SQL ด้วย incremental parsing เพื่อหลีกเลี่ยงผลลัพธ์ที่ผิดไวยากรณ์ บทเรียนที่ย้ายมาได้คือควบคุม formal output แต่ความถูกไวยากรณ์ไม่ได้รับรองว่าเลือกงานและข้อมูลตรงคำถาม

**นำมาใช้:** JSON schema จำกัด task/slot/ID แล้วตรวจความหมาย ชนิด relation ตัวเลข และ negation แยกอีกชั้น; R95 มี JSON constraints อยู่แล้ว จึงต้องแก้ชั้น semantics เพิ่ม

[บทความ](https://aclanthology.org/2021.emnlp-main.779/)

### P05 — IRCoT, ACL 2023

งานแสดงข้อจำกัดของการ retrieve ครั้งเดียวในคำถามหลายขั้น และสลับการค้นกับขั้นเหตุผลเพื่อหาหลักฐานต่อเนื่อง การทดลองเป็น open-domain QA ต่างจากธุรกิจศูนย์นี้

**นำมาใช้:** dependency-aware reads ที่ตรวจได้ เช่น หาเกม→โซน→บริการ→ราคา; ใช้แผนมีโครงสร้างและขอบเขต ไม่เพิ่ม chain-of-thought ยาวหรือ agent loop ไม่จำกัด

[บทความ](https://aclanthology.org/2023.acl-long.557/)

### P06 — Sufficient Context, ICLR 2025

งานแยกความเพียงพอของ context ออกจากพฤติกรรมตอบ/งดตอบ พบว่ามีความผิดพลาดได้แม้ข้อมูลพอ และเสนอใช้ sufficiency ร่วมกับ confidence ข้อจำกัดสำคัญคือ autorater ยังผิดได้ และบริบทงานทดลองไม่ใช่นโยบายร้าน

**นำมาใช้:** ตรวจต่อ need ว่าหลักฐานพอสำหรับ claim ที่ถามหรือไม่ พร้อมแยก false abstention จาก justified abstention ระบบนี้ต้องเข้มกว่าการใช้ความรู้ในพารามิเตอร์สำหรับราคาและนโยบายเจ้าของ

[บทความและข้อจำกัดเชิงวิธี](https://arxiv.org/html/2411.06037v3)

### P07 — Clarify When Necessary, Findings of NAACL 2025

งานศึกษาเมื่อไรควรถามเพิ่ม โดยคำนึงถึงความต่างของการตีความและต้นทุนการโต้ตอบ มีวิธี IntentSim ประเมินความไม่แน่นอนระดับเจตนา ผลไม่ใช่เหตุให้ใช้ค่า confidence ของตัวเองเป็นใบอนุญาตเดา

**นำมาใช้:** ถามเฉพาะ slot ที่ทำให้คำตอบเปลี่ยน เช่น หมายถึงกติกาแข่งหรือเครื่องใช้งานทั่วไป; คำว่า please หรือคำผิดที่มีเป้าหมายเดียวไม่ควรทำให้ต้องเริ่มถามหัวข้อใหม่

### P08 — RAGChecker, 2024

งานแยกการประเมิน retrieval และ generation เป็นระดับ claims รวมถึง recall, faithfulness และการใช้ context ข้อจำกัดที่ผู้เขียนระบุรวมถึง benchmark ภาษาอังกฤษ และไม่แยก neutral/contradiction ในบาง metrics

**นำมาใช้:** trace ว่า claim ที่จำเป็นหายตั้งแต่ retrieval หรือหายตอนตอบ แยกไม่มีหลักฐานออกจากขัดแย้งโดยตรง ประเมินไทย/อังกฤษด้วยชุดของเรา ไม่ถือว่าตัว judge ในงานใช้แทนได้ทันที

[บทความ รวม Appendix H](https://arxiv.org/html/2408.08067v1)

### P09 — CheckList, ACL 2020

งานเสนอการทดสอบพฤติกรรมผ่าน minimum functionality, invariance และ directional expectations ช่วยพบข้อบกพร่องที่คะแนนเฉลี่ยไม่แสดง

**นำมาใช้:** คำถามเป้าหมายเดียวหลายสำนวน/คำผิดต้องคงคำตอบ ขณะที่เปลี่ยนกลุ่มผู้ใช้ วัน หรือ negation ต้องเปลี่ยนตามหลักฐาน แบ่งกลุ่มทดสอบตามสมรรถนะ ไม่เพิ่มแค่จำนวนคำถามคล้ายกัน

[บทความ](https://aclanthology.org/2020.acl-main.442/)

### P10 — Semantic Answer Similarity, MRQA 2021

งานเสนอ cross-encoder similarity และพบความสัมพันธ์กับการประเมินมนุษย์ที่ดีกว่าตัววัด lexical บนชุดที่ศึกษา ซึ่งเป็นอังกฤษ/เยอรมัน ไม่ได้ยืนยันการตรวจไทยหรือนโยบายที่มีข้อยกเว้น

**นำมาใช้:** เพิ่ม semantic comparison เป็นตัวช่วยจัดคิว แต่ตัวเลข ระยะเวลา เงื่อนไข และการอนุญาตต้องมีตัวตรวจเฉพาะ ห้ามใช้ cosine similarity สูงตัดสินว่าคำตอบถูก

[บทความ](https://aclanthology.org/2021.mrqa-1.15/)

### P11 — FreshLLMs / FreshQA, Findings of ACL 2024

งานประเมินความรู้ที่เปลี่ยนตามเวลาและคำถามที่มีสมมติฐานผิด โดยใช้หลักฐานใหม่และแยกการประเมินหลายระดับ การค้นเว็บในงานไม่ได้ให้อำนาจระบบเราแทนที่ข้อมูลเจ้าของ

**นำมาใช้:** แยก current/historical/live และตรึงวันที่ใน evaluator ประเมินการไม่ยืนยันราคาหมดอายุให้ถูกประเภท ไม่ต่ออายุหรือเติมนโยบายเพื่อไล่คะแนน

[บทความ](https://aclanthology.org/2024.findings-acl.813/)

### P12 — Lost in the Middle, TACL 2024

งานศึกษาความไวต่อการวางตำแหน่งข้อมูลใน context ยาว แสดงว่าความจุ context ไม่เท่ากับใช้ข้อมูลได้ดีเสมอ

**นำมาใช้:** ส่ง evidence เฉพาะ need โดยมีเงื่อนไขที่จำเป็นครบ จัดส่วนสำคัญให้ชัด ไม่ยัดทุก record/ทุกข้อกฎเข้า prompt เพื่อหวังว่าความครบจะเพิ่มเอง; ยังไม่พิสูจน์ว่าเป็นสาเหตุของ timeout R95

[บทความ](https://aclanthology.org/2024.tacl-1.9/)

### P13 — M3-Embedding / BGE-M3, Findings of ACL 2024

งานนำเสนอ representation สำหรับหลายภาษาและทั้ง dense/sparse/multi-vector retrieval เป็นหลักฐานตัวเลือกการค้นข้ามภาษา ไม่ใช่คำรับรองเรื่องคำผิดไทยในศูนย์นี้

**นำมาใช้:** ทดลอง hybrid retrieval หลังวัด candidate recall ว่าเป็นคอขวดจริงเท่านั้น ต้องวัด RAM/VRAM/latency ร่วมกับโมเดล 4B ก่อนเพิ่ม ไม่ใช้ embedding เพื่อแปลกฎหรือยืนยันราคา

[บทความ](https://aclanthology.org/2024.findings-acl.137/)

### P14 — Corrective RAG, arXiv 2024

งานใช้ retrieval evaluator และการเลือกแนวทางแก้เมื่อเอกสารที่ค้นมาคุณภาพไม่ดี มีองค์ประกอบค้นเว็บและคัดข้อมูลซึ่งไม่ตรงกับ source authority ของร้านทุกส่วน

**นำมาใช้:** bounded corrective read ภายในข้อมูลกลางที่อนุญาต เช่น จาก game record ไป competition clauses; ไม่เปิดเว็บมาเติมนโยบายสดอัตโนมัติ และไม่วนเรียก LLM จนได้คำตอบที่ดูผ่าน

[บทความ](https://arxiv.org/html/2401.15884v3)

### P15 — Self-RAG, ICLR 2024

งานฝึกโมเดลให้เลือกค้นและวิจารณ์การรองรับของคำตอบผ่าน reflection tokens เป็นวิธีที่มีการฝึกเฉพาะ ไม่เท่ากับถามโมเดลเดิมว่า “ตรวจตัวเองอีกที”

**นำมาใช้:** ใช้แนวคิดตรวจ relevance/support เป็นโจทย์เสริมภายหลัง หากแผน deterministic และ sufficiency ยังไม่พอ ไม่เริ่มด้วยการเพิ่ม self-reflection หลายรอบบน 4B เพราะไม่มีหลักฐานด้านคุณภาพและเวลาในระบบนี้

[บทความ](https://arxiv.org/abs/2310.11511)

## 7. สิ่งที่งานวิจัยไม่ได้พิสูจน์ให้เรา

- เพิ่มข้อมูลลง schema แล้วจะตอบได้ทุก paraphrase โดยไม่ต้องมี task coverage
- เพิ่มโมเดลใหญ่/embedding/long context แล้วแก้ข้อมูลหมดอายุหรือ relation ผิดได้เอง
- JSON ถูก รูปคำตรง หรือมี citation แล้วคำตอบถูกครบ
- โมเดลเดียวเลือกข้อมูล สร้างคำตอบ และให้คะแนนตัวเอง จะตรวจจับความผิดได้อย่างอิสระ
- คะแนนจาก English open-domain benchmark ย้ายมาเป็นไทย/อังกฤษของร้านนี้ได้เท่ากัน
- ความสามารถเขียน schema ใหม่จาก prompt เท่ากับพร้อมใช้งานธุรกิจใหม่ที่มีวิธีคำนวณใหม่

## 8. ข้อสรุปเพื่อเลือกแนวทาง

เลือกการพัฒนาแบบ **shared task interpretation + common fact provider + deterministic domain execution + per-need evidence checks** โดยเก็บบทเรียนจาก Legacy เป็น logic และตัวอย่างระดับงาน ให้ข้อมูลใหม่อ่านผ่าน interface เดียวกัน

เริ่มจาก failure attribution และ regression ที่มีข้อมูลเพียงพอ ก่อนเพิ่มระบบ retrieval หรือฝึกโมเดล เพราะ log มีตัวอย่างชัดว่าเจอข้อมูลแล้วก็ยังไม่ตอบ และ 498 คำถามในกลุ่มไม่ผ่านเกี่ยวกับ not_current ซึ่งเปลี่ยนโมเดลไม่แก้ความจริงของข้อมูล
