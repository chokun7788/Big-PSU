# ตรวจเจตนาคำถามปุ่มเกมและราคา PC

ตรวจผล source-only ที่เก็บไว้ของคำถาม “Tekken 8 ปุ่มอะไร แล้ว PC ราคาเท่าไหร่” พบว่างานราคาได้รับสถานะ `invalid_plan` พร้อมเหตุผล `source_receipt_verification_failed` และ `hybrid_independent_calculation_unproven` ก่อนถูกแสดงเป็น “ยังไม่มีข้อมูลยืนยันสำหรับส่วนที่ถาม”

ตรวจ source index ของคำถามย่อย “PC ราคาเท่าไหร่” พบ rate candidates 12 รายการ และ service ที่ตรง 2 รายการ โดยไม่ได้ระบุ audience ในคำถาม ผลนี้เพียงยืนยันว่ามี candidates ไม่ได้ยืนยันว่าราคาทั้ง 12 รายการใช้ได้หรือว่า audience เป็นข้อมูลเดียวที่ขาด การตรวจระยะเวลา ขอบเขต service และ source validity ยังจำเป็น

ข้อสรุป: ยังเปลี่ยนข้อความเป็นถาม audience ทันทีไม่ได้ เพราะสาเหตุที่บันทึกไว้เป็นการตรวจ calculation/receipt ล้ม ต้องตรวจ input ของ verifier และแยกว่าเป็น unit rate ที่แสดงได้โดยไม่ต้องคิดยอดรวม หรือเป็นยอดรวมที่ขาดเงื่อนไข จากนั้นทดสอบกรณีมี/ไม่มี audience และ duration รวมถึง source ที่ไม่มี rate จริงและคำถามสองส่วน

ยังไม่มีการแก้ runtime หรือทดสอบโมเดลในรอบวิเคราะห์นี้ ผลเดิมและหลักฐานคำตอบอยู่ `natural_delivery_1794131016058503200/DETAILS.json` ในโฟลเดอร์ทดลองบน D:.

ตรวจ executor artifact เพิ่ม: งานปุ่มเกม `t1` เป็น supported และมี 12 claims; งานราคา `t2` เป็น invalid_plan โดย executor ที่ส่งออกมี 0 claims และ 0 calculation receipts หลังถูกปฏิเสธ จึงใช้ artifact ปลายทางนี้เพียงอย่างเดียวระบุค่าคำนวณที่ทำให้ verifier ล้มไม่ได้ ต้องเก็บ input ก่อน assess จากการทดลองในฐานสำเนา แล้วเทียบคำถามราคาเดี่ยวกับคำถามผสมก่อนแก้ ไม่ตีความว่า source ไม่มีราคาจาก 0 claims หลังถูกปฏิเสธ

9 พ.ย.: `pc_assessment_1794163037792720700/DETAILS.json` เก็บ input ก่อน assess จากฐานสำเนาโดยไม่เรียกโมเดล: ทั้งราคา PC เดี่ยวและคำถามผสมมี 6 claims/6 calculations สำหรับหลาย audience แล้วถูก `hybrid_independent_calculation_unproven` เหมือนกัน ตัวตรวจ `calculation_check.errors` เข้าสาขาหลาย audience ซึ่งต้องผูกจำนวนคนแต่ละกลุ่ม แม้คำถามตัวอย่างถามราคาโดยไม่ระบุจำนวนคน ทั้งนี้ต้องแยก unit-rate alternatives ออกจากการขอยอดรวม และตรวจ applicability/source/การปลอมก่อนเปลี่ยน guard; ยังไม่ได้แก้ runtime รอบนี้ เก็บ harness แรกที่ import ตำแหน่ง assess ผิดไว้ใน pc_assessment.latest.log และฉบับแก้ใน pc_assessment.corrected.log

รอบถัดมาแก้ experimental candidate ให้ตรวจอัตราหลายกลุ่มเป็นรายการต่อหน่วยเมื่อไม่มีจำนวนคนและไม่มีคำขอยอดรวม พร้อมปฏิเสธยอดรวมที่แสดงในกรณีนี้ Direct guard ผ่าน 12 controls (`alternative_rate_guard_1794224181169793300`); คำถามเดี่ยวและผสมในฐานสำเนาไม่ถูก fatal เดิมแล้ว (`pc_assessment_1794224199841226200`). currency regression 12 และ compound duration 11 ผ่าน source-only. พบผลข้างเคียงที่ยังเปิด: คำตอบราคา PC แสดงอัตราซ้ำ 2 ชุดจาก service 2 records ซึ่งยังไม่ได้พิสูจน์ว่าเป็นบริการเดียวกัน จึงไม่ dedupe แบบเดา ต้องตรวจความสัมพันธ์และทดสอบ source แก้/ถอน รวมทั้งถามยอดรวม หลายจำนวนคน ภาษาอังกฤษ และ verifier/formatter ก่อนรับ candidate ไม่มี model/HTTP/authority/production proof และยังไม่ติดตั้ง

การตรวจรอบถัดมาพบ direct forced output แบบ “ราคารวมเป็น 165 บาท” และ “The total is 165 THB” หลุด guard เดิม (`alternative_rate_guard_1794224342388951600` ล้ม 4 controls) จึงปรับ guard ทดลองให้จับรูปแบบเหล่านี้ด้วย: replay `alternative_rate_guard_1794224376188487000` ผ่าน 16 controls, currency regression 12 และ compound duration 11 ผ่าน ผลทั้งหมดเป็น source-only โดย forced output ไม่พิสูจน์ว่าข้อความปลอมถูกส่งจริง และ regex ไม่พิสูจน์ว่าตรวจรูปแบบยอดรวมได้ทุกแบบ ปัญหาราคาซ้ำและ source/semantic/full-flow gates ยังเปิด

ตรวจ source พบ service IDs แยกเครื่อง `availability_pc_01_02` กับ `availability_pc_03_10` มีชื่อเครื่องและ resource IDs คนละชุด จึงไม่รวม records: renderer candidate แสดงชื่อบริการจาก source เมื่อมีหลาย service ใน platform เดียว ทำให้ผู้ใช้แยกสองชุดได้ แชต source-only คำถามเดี่ยวและผสม `pc_assessment_1794228133221331100` แสดงชื่อทั้งสองชุด; renderer controls `pc_service_labels_1794228208876819000` ผ่าน 6 รวม English, single service, จำลองเปลี่ยนชื่อใน index และชื่อ unknown; currency 12 และ alternative rate guard 16 ผ่านหลังแก้ การจำลองแก้ index ไม่ใช่การแก้ source ผ่าน owner API และยังไม่พิสูจน์ validity/authority หรือ model/HTTP การแสดงจำนวนบรรทัดยังมี 6 รายการ จำเป็นต้องรักษาขอบเขต source; การแสดง grouped summary และการแก้/ถอนผ่าน owner ยังต้องตรวจ ไม่มี full 5%/deploy
