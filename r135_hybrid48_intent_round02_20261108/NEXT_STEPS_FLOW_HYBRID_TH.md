## 1. ฐานปัจจุบันที่ใช้ต่อ

- แก้คำเตือนระยะเวลาที่ขัดกับราคาสำหรับคำถามราคา Cockpit พร้อมวิธีจองแล้ว มีหลักฐาน source-only ไทย/อังกฤษและ direct mutations ใน `INTENT_DURATION_FIX_20261108.json`
- ตัวตรวจราคาแยกการแสดงอัตราของหลายกลุ่มออกจากการขอยอดรวมในขอบเขตที่ทดสอบแล้ว แต่ guard ข้อความยอดรวมยังใช้ regex บางส่วน จึงยังไม่รับรองข้อความทุกแบบ
- ราคา PC มาจากบริการคนละกลุ่มเครื่อง `PC #01–#02` และ `PC #03–#10` ปัจจุบัน candidate แสดงชื่อบริการกำกับ โดยเก็บทั้งสอง source records ไว้
- การเปลี่ยนชื่อที่ตรวจล่าสุดเป็นการจำลองใน source index ยังไม่ใช่การแก้ผ่าน owner workflow
- ยังไม่มีผล 5% รอบใหม่ของ candidate นี้ และยังไม่ได้ติดตั้งแทนตัวแชตที่เปิดใช้อยู่
- หลักฐานรุ่นเดิมใช้ได้เฉพาะส่วนที่ code/data/config ยังตรงกัน ห้ามยก `ready_for_eval` ของรุ่นเดิมมาเป็นสถานะพร้อมของ candidate นี้

## 3. วิธีทำแต่ละกลุ่ม

### งาน 1 — ตรึงปัญหาและชุดตรวจ

- [ ] อ่าน `STATUS.json`, หลักฐานล่าสุด และ git diff ก่อนแก้
- [ ] จัดรายการปัญหาที่เหลือจากผลเดิมเป็นกลุ่มสาเหตุ ไม่เรียงแก้ทีละคำถาม
- [ ] ต่อกลุ่มให้บันทึก: คำถามจริง, เจตนา, ผลที่ควรได้, ผลที่เกิด, source ที่เกี่ยวข้อง และจุดที่ต้องเปลี่ยน
- [ ] เลือกชุดตรวจสั้นก่อนแก้ ประกอบด้วยกรณีที่เคยล้ม กรณีปกติ กรณีที่ต้องปฏิเสธ และ regression ที่กระทบ
- [ ] ระบุว่ากรณีใดใช้ผลเดิมต่อได้ พร้อม code/data/config ที่รองรับ

**เกณฑ์จบ:** รู้ว่าจะเปลี่ยนอะไรและตรวจอะไร โดยไม่เริ่มรันทั้งชุดเพื่อหาสาเหตุที่มีอยู่ใน log แล้ว

### งาน 2 — ข้อมูลเพิ่ม/แก้/ถอนจริงในฐานสำเนา

ทำก่อนการย่อหรือรวมตารางราคา เพราะต้องมั่นใจว่าการจัดคำตอบไม่ซ่อนข้อมูลใหม่หรือข้อมูลที่เปลี่ยน

- [ ] สร้าง DB สำเนาด้วย SQLite backup และเก็บ epoch/revision ตั้งต้น
- [ ] เพิ่มบริการทดลองที่มี platform เดียวกับ PC แต่ชื่อและขอบเขตต่างกัน แล้วตรวจว่าตอบเป็นคนละบริการ
- [ ] แก้ชื่อบริการหนึ่งกลุ่มผ่าน owner save operation ที่ระบบใช้จริง แล้วถามใหม่โดยใช้ reader instance เดิมด้วย เพื่อตรวจ cache
- [ ] แก้ราคาเพียงกลุ่มเดียว ตรวจว่าคำตอบเปลี่ยนเฉพาะกลุ่มนั้นและอีกกลุ่มยังอยู่
- [ ] ถอน rate หนึ่งรายการ ตรวจข้อความ claims และ receipts ว่าไม่อ้าง record ที่ถอน โดยยังตอบรายการอื่นที่ใช้ได้
- [ ] เพิ่ม rate ใหม่ ตรวจว่าค้นพบและตอบได้จริง ไม่ใช่ผ่านเพราะไม่มี claims
- [ ] ตรวจว่า confirmation เดิมที่ไม่ตรงเนื้อหาใหม่ไม่ถูกนำมาอ้างต่อ
- [ ] ปลอม snapshot/locator ของ record เก่า แล้วตรวจว่าตัวตรวจปฏิเสธ

**เกณฑ์จบ:** มีคำตอบก่อน–หลังและ revision/source refs ประกอบครบ การตรวจผ่านต้องมี positive ที่ยังตอบได้ พร้อม negative ที่ถูกระงับ

**ข้อจำกัด:** owner function ระดับ Python พิสูจน์เส้นทาง save ระดับนั้นเท่านั้น การกดผ่านหน้า editor และ HTTP ต้องตรวจเพิ่มในงาน 8

### งาน 3 — ราคา alternatives กับยอดรวม

- [ ] แยกเจตนา “ราคา PC เท่าไหร่” ออกจาก “พวกเรารวมต้องจ่ายเท่าไหร่” และ “เปรียบเทียบราคา”
- [ ] คง service ID, audience, หน่วย, ช่วงคน, ระยะเวลา และ source ที่ใช้ในแต่ละบรรทัด
- [ ] คำถามราคาโดยไม่ระบุจำนวนคนแสดงอัตราต่อหน่วยได้เมื่อมีหลักฐาน ไม่สมมติเป็นการซื้อของทุกกลุ่มผู้ใช้
- [ ] คำถามยอดรวมที่มีข้อมูลครบต้องได้ยอดที่คำนวณย้อนกลับได้
- [ ] จำนวนคนหรือบทบาทไม่ชัด ต้องถามหรือแจ้งส่วนที่ยังคำนวณไม่ได้
- [ ] ทดสอบยอดรวมปลอมทั้ง structured computations และข้อความหลัง formatter รวมไทย/อังกฤษ
- [ ] ตรวจว่าการรวมยอดอ้าง source และ quantities โดยตรง ไม่เชื่อเพียงค่าที่ reader ส่งมา
- [ ] ถ้าจะย่อหกบรรทัดเป็นตาราง ต้องคงความต่างของสองกลุ่มเครื่องและ citations ไม่รวม records เพียงเพราะราคาเท่ากัน

**เกณฑ์จบ:** อัตราที่แสดงไม่ถูกอ้างเป็นยอดซื้อ กรณีคำนวณได้ยังผ่าน กรณีปลอมไม่ผ่าน และการจัดรูปแบบไม่เปลี่ยนจำนวนเงินหรือขอบเขต

### งาน 4 — ถามข้อมูลที่ขาดให้ตรงจุด

- [ ] แยกสถานะอย่างน้อย: ไม่เข้าใจงาน / ขาดข้อมูลผู้ถาม / ขาด source / ข้อมูลขัดแย้ง / verifier ปฏิเสธ / โมเดลหรือ provider ไม่พร้อม
- [ ] ถ้ามีอัตราให้เลือกแต่ยังระบุกลุ่มผู้ใช้ไม่ได้ ให้ถามเฉพาะข้อมูลที่จะทำให้เลือกคำตอบได้
- [ ] ถ้าถามอัตราต่อชั่วโมงอยู่แล้ว ไม่บังคับให้บอกระยะเวลารวมโดยไม่มีเหตุจำเป็น
- [ ] ถ้า source ไม่มีราคาจริง ให้แจ้งว่าไม่พบอัตราที่ยืนยันได้ แทนการถามซ้ำแบบไม่มีทางตอบสำเร็จ
- [ ] ถ้าคำถามหลายส่วนตอบได้บางส่วน ให้ส่งส่วนนั้นและถามเพิ่มเฉพาะส่วนที่ขาด
- [ ] ตรวจกรณีข้อมูลครบอยู่แล้วว่าไม่ถามซ้ำ

**เกณฑ์จบ:** แต่ละคำถามติดตามมีเหตุผลและผูกกับ task ที่ขาด ผู้ใช้ตอบเพิ่มแล้วระบบสามารถใช้ข้อมูลนั้นต่อได้โดยไม่ปะปนกับ task อื่น

### งาน 5 — วิเคราะห์หลายความต้องการและจัดคำตอบ

- [ ] ใช้ตัวแทนกลุ่ม ราคา+จอง / ปุ่มเกม+ราคา / ที่อยู่+จอง / เวลาเปิด+สถานะว่าง
- [ ] ตรวจทั้งไทยและอังกฤษ รวมคำสะกดผิดที่มีหลักฐานว่ารองรับแล้ว
- [ ] เก็บ raw question และตรวจ source spans ว่าย้อนกลับไปยังต้นฉบับได้
- [ ] ตรวจว่าจำนวนคน เวลา เกม และบริการมี task เจ้าของชัดเจน
- [ ] ชื่อเกมที่มีคำว่า and/เครื่องหมายคั่นและวลีมีเงื่อนไขต้องไม่ถูกแยกผิด
- [ ] ขึ้นต้นด้วยคำตอบที่ถาม ตามด้วยเงื่อนไข ส่วนเสริม และสิ่งที่ยังต้องถาม
- [ ] ตรวจคำตอบหลัง formatter พร้อม claims/receipts และ terminal state ว่าตรงกัน

**เกณฑ์จบ:** งานที่รู้จักไม่ตกหล่น ส่วนที่ไม่รู้จักมี disclosure และไม่มีสถานะว่า “ครบ” ทั้งที่คำถามยังตอบไม่ครบ

### งาน 6 — เป้าหมาย เกม อุปกรณ์ และแพลตฟอร์ม

- [ ] ตรวจเกมชื่อคล้ายกัน คนละภาค และแพลตฟอร์มที่ไม่ได้ระบุ
- [ ] แยก “มีข้อมูลปุ่มบนแพลตฟอร์มนี้” ออกจาก “ศูนย์มีเกมบนแพลตฟอร์มนี้ให้เล่น”
- [ ] กรณี source ไม่ระบุ input_device ให้คงความไม่แน่ใจ ไม่เดาจาก platform อย่างเดียว
- [ ] อุปกรณ์ “ใช้ยังไง” ต้องเลือกข้อมูล usage ไม่ส่งเพียง specs
- [ ] ชื่อหรือรายละเอียดของอีกหน่วยงานต้องไม่กลายเป็นข้อมูลศูนย์นี้

**เกณฑ์จบ:** positive ตอบเป้าหมายที่ถูก และ negative ไม่ใช้ข้อมูลของเป้าหมายอื่นมาชดเชย ส่วน operator/authority ที่ source ผูกไม่ได้คงเป็นข้อจำกัดเปิด ไม่ hardcode เพื่อให้คะแนนผ่าน

### งาน 7 — เส้นทางโมเดลและสาเหตุไม่พร้อม

- [ ] ตรวจ process/health/ชื่อโมเดล/retained profile โดยไม่หยุด protected model
- [ ] ใช้ logs เดิมแยก admission, transport, response parsing, source binding และ verifier rejection
- [ ] เมื่อเส้นทางเรียกได้รับอนุญาตและพร้อม ให้ทดสอบตัวแทนทีละคำถาม รอข้อก่อนจบก่อนส่งข้อใหม่
- [ ] จับคู่คำถามกับ model-call receipt และคำตอบจริง บันทึกเวลารอและเวลาประมวลผลแยกกัน
- [ ] ความผิดพลาดระบบต้องคงเป็น error ไม่แปลงเป็น “ไม่มีข้อมูล”
- [ ] งานเตรียม sequential evaluation ที่เคยถูก automatic approval review ปฏิเสธต้องตรวจสถานะที่อนุญาตจริงก่อนทำ ห้ามเปลี่ยนเครื่องมือหรือ path เพื่อเลี่ยงการปฏิเสธนั้น

**เกณฑ์จบ:** มีหลักฐานจากการเรียกจริงของเส้นทางที่เปิดใช้ หรือระบุ blocker ให้ชัด ยังใช้ผล source-only ปิดงานนี้ไม่ได้

### งาน 8 — รวม candidate และตรวจผ่านแชต/editor จริง

- [ ] เปิด candidate แยก port, DB, state และ log ของตนเอง พร้อม build identity ที่แยกจากรุ่นเก่า
- [ ] ตรวจว่าคำถามจากหน้าแชตผ่าน snapshot, task graph และ verifier ชุดที่ทดสอบจริง
- [ ] ตรวจราคา จอง และคำถามผสมตัวแทน พร้อม error/partial response
- [ ] ใช้ owner workflow ผ่าน HTTP/editor เพิ่ม แก้ ถอนใน DB ทดลอง และถามใหม่ผ่าน HTTP
- [ ] ตรวจ runtime log ว่าเก็บ raw question, source revision, claims, receipts, reason codes และสถานะส่งคำตอบได้ โดยไม่เปิดเผย token

**เกณฑ์จบ:** ช่องทางใช้งานจริงตรงกับ candidate ที่ตรวจและข้อมูลที่เปลี่ยนมีผลต่อคำตอบ ไม่ใช่ผ่านเฉพาะการเรียกฟังก์ชันโดยตรง

### งาน 9 — ตรวจความครอบคลุมก่อนรอบรวม

- [ ] ทำตาราง category + operation + field ของทั้ง 14 หมวด ระบุ R135 / R134 compatibility / clarify-or-withhold
- [ ] ใช้หลักฐานเดิมที่ยังตรงกันและเติมเฉพาะช่องว่าง โดยเฉพาะ list/count/compare
- [ ] เสริม controlled cases สำหรับ C07 ซึ่ง manifest 5% เดิมมีเพียงหนึ่งตัวอย่าง โดยรายงานแยกจากคะแนน 5%
- [ ] ตรวจเฉพาะ dependency จากข้อกำหนด 76/14 ที่จำเป็นต่อรุ่นทดลอง และรักษารายการค้างของ R135 เต็ม

**เกณฑ์จบ:** ความสามารถที่เปิดทุกตัวมีหลักฐานและข้อจำกัดระบุไว้ ไม่มีการนับว่าทั้งหมวดผ่านจากการอ่านหนึ่ง record สำเร็จ

### งาน 10 — รอบรวม 5% แบบทีละคำถาม

เริ่มเมื่อกลุ่มสำคัญข้างต้นผ่านและช่องทางรันพร้อมแล้ว

- [ ] ใช้ manifest เดิม 1,056 คำถาม ไม่สุ่มใหม่ และตรวจ key/count/hash ก่อนรัน
- [ ] ตรึง code, DB snapshot, config, model identity และเวลาอ้างอิง พร้อมยืนยันว่า editor ไม่แก้ DB ที่กำลังวัด
- [ ] ใช้ worker เดียว ส่งข้อใหม่หลังข้อก่อนจบ บันทึก timeout/error ตามจริง ไม่ retry เงียบ
- [ ] บันทึกผลแบบ append-only และมี progress/PID/error log ตรวจสอบได้
- [ ] ห้ามแก้ runtime ที่กำลังวัด และห้ามเริ่มการวัดซ้อน
- [ ] ตรวจจำนวนผลครบและไม่มีคำถามหลุด/ซ้ำก่อนให้คะแนน
- [ ] รายงาน literal matched/not matched/unassessed พร้อมตัวหารและเกณฑ์ที่ไม่รองรับ
- [ ] เทียบ saved R134 เฉพาะ keys และเกณฑ์เดียวกัน พร้อมข้อจำกัด source/time/backend ที่ต่างกัน
- [ ] ใช้การทบทวนเจตนาและ source โดย GPT กับกรณีที่เปลี่ยน/ขัดแย้ง และตัวแทนหมวด โดยระบุจำนวนที่ตรวจจริง ไม่ขยายเป็น semantic accuracy ของทั้งชุด

**เกณฑ์จบ:** ผลรันและรายงานตรวจย้อนกลับได้ HTTP สำเร็จไม่ถูกนับเป็นคำตอบถูก และไม่ rerun/regrade R132

### งาน 11 — แก้จากผลรวมเป็นกลุ่ม

- [ ] จัดข้อผิดตามสาเหตุร่วมและจำนวนคำถามที่กระทบ
- [ ] ให้ความสำคัญกับผิดเป้าหมาย ผิดเงิน ข้อมูลถอนหลุด และตอบว่าครบทั้งที่ไม่ครบ ก่อนปัญหาความยาวหรือรูปแบบ
- [ ] แก้หนึ่งกลุ่มและตรวจชุดที่เกี่ยวข้องหนึ่งรอบหลังการเปลี่ยน
- [ ] รัน 5% ใหม่เฉพาะเมื่อมีการเปลี่ยนรวมที่กระทบระบบหรือพบปัญหาการเชื่อมต่อที่ focused tests ตรวจไม่ถึง

**เกณฑ์จบ:** ทุก known critical failure ได้รับการแก้หรือปิดเส้นทางนั้นพร้อมข้อจำกัด ไม่มีการเพิ่มคะแนนด้วยการตัดกรณียากออกจาก manifest

### งาน 12 — ส่งมอบรุ่นทดลอง

- [ ] มีหน้าสรุปเปิดอ่านคำถาม คำตอบ ผลตรวจ และเหตุผลที่ยังประเมินไม่ได้
- [ ] มีรายการความสามารถที่รองรับ/ยังไม่รองรับ พร้อมขอบเขตและหลักฐาน
- [ ] มีวิธีเปิด candidate บน D: และระบุชัดว่าเป็น build ใด
- [ ] ก่อนแทนตัวใช้งานจริง ต้องผ่าน gates ที่เกี่ยวข้อง สำรอง DB รวม WAL และมี rollback
- [ ] เก็บ code/แผน/สรุปขึ้น Big-PSU ส่วน DB/model/raw logs/private chat เก็บบน D: ตามที่ผู้ใช้เลือก

**เกณฑ์จบ:** ทดลองใช้งานในขอบเขตที่ประกาศได้และมีทางย้อนกลับ ไม่ประกาศว่ารับรอง R135 ครบทั้ง 76 ข้อโดยอาศัยผลรอบนี้

## 4. กติกาที่ทำให้งานเร็วขึ้น

1. ก่อนแก้หนึ่งกลุ่ม ให้กำหนดผลที่คาดและชุดตรวจที่จะใช้ให้จบในครั้งเดียว
2. เก็บ failure ก่อนแก้ หากมีหลักฐานเดิมที่ code/data/config ตรงกันให้ใช้ต่อ ไม่รันเพื่อยืนยันเรื่องเดิมอีก
3. แก้สาเหตุร่วม ไม่ hardcode ตามข้อความของคำถามทดสอบ
4. หลังแก้ ตรวจกรณีล้มเดิม + positive + negative + affected regression หนึ่งรอบ
5. อ่านคำตอบจริงและ structured artifacts ไม่ตัดสินจาก exit code เพียงอย่างเดียว
6. ถ้าล้มแนวทางเดิมสองรอบ ให้บันทึกเหตุผลและเปลี่ยนวิธีหรือพัก capability แล้วเดินงานที่ไม่ติด blocker ต่อ
7. Harness/import/fixture ผิดต้องแยกจากโปรแกรมผิด แก้ harness แล้วตรวจเฉพาะส่วนที่ผลเดิมยังใช้ไม่ได้
8. ไม่รัน 1,056 ข้อทุกครั้งที่แก้หนึ่งจุด ไม่รันโมเดลซ้ำเพื่อแก้ assertion ที่ตรวจคำตอบที่เก็บไว้ได้
9. รายงานทุก 6 ชั่วโมงตามสิ่งที่ทำจริง: กลุ่มที่เปลี่ยน ผลใหม่ ข้อจำกัด และงานถัดไป ไม่อ้างทำต่อเนื่องระหว่างรอบหากไม่มีหลักฐาน

## 5. สิ่งที่ต้องบันทึกต่อกลุ่ม

| รายการ | เนื้อหา |
|---|---|
| ปัญหา | ตัวอย่างคำถาม เจตนา ผลที่เกิด และผลที่คาด |
| สาเหตุ | หลักฐานจาก source/trace และส่วนที่ยังเป็นสมมติฐาน |
| การแก้ | ไฟล์ที่เปลี่ยนและ code hashes |
| การตรวจ | ชุดที่เลือก เหตุผลที่เลือก ผลก่อน–หลัง และผลที่ล้ม |
| ขอบเขต | source-only / function / HTTP / model / owner lifecycle ที่ตรวจจริง |
| งานค้าง | กรณีที่ยังไม่ครอบคลุมและ blocker |
| สถานะ | ยังทดลอง / ผ่านเฉพาะกลุ่ม / พร้อมรวม / พร้อมวัด / พร้อมส่งรุ่นทดลอง |

ไม่ประมาณเวลาจบจากการเปิดเครื่องทิ้งไว้ ใช้เวลาลงมือ เวลารัน และจำนวนกลุ่มที่ผ่านจริงเพื่อปรับประมาณการเมื่อมีข้อมูลพอ
