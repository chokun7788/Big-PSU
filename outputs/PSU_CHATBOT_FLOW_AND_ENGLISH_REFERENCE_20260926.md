# PSU Esports Studio Phuket Chatbot — สถานะ flow และภาษาอังกฤษ (26 ก.ย. 2026)

## สิ่งที่ระบบทำอยู่

WordPress export ของระบบจองเผยแพร่ไฟล์ `wbk_appointments.csv` และ `wbk_services.csv` → Dashboard ภายในเครื่องอ่านไฟล์เหล่านั้นเมื่อมีคำขอ → Chatbot อ่าน `/api/chatbot-status` ที่พอร์ต 8091 แล้วตอบสถานะเครื่อง/ช่องตามวันและเวลา โดย endpoint สำหรับ Chatbot ส่งเฉพาะยอดรวมและ slot ไม่ส่งข้อมูลผู้จอง

`start-dashboard.bat` ใน D: เปิดโปรแกรม Dashboard ท้องถิ่น จึงต้องเปิดค้างไว้หากใช้ Dashboard ชุดนั้น แพ็กเกจ Chatbot r3 มี Dashboard ชุดเดียวกันอยู่ภายในและเปิดเบื้องหลังเมื่อเริ่ม Chatbot: ผู้ใช้เห็นเฉพาะหน้า Chatbot ที่พอร์ต 8080 ได้ จึงไม่ต้องเปิด D: bat พร้อมกัน เพราะทั้งสองแย่งพอร์ต 8080 ชุด r3 มี `Open-PSU-Esports-Background.cmd` สำหรับเริ่มแบบไม่ต้องค้างหน้าต่างคำสั่ง แต่เครื่องและกระบวนการต้องยังทำงาน; ยังไม่มีการตั้งให้เริ่มอัตโนมัติหลัง Windows เข้าระบบหรือเปิดใหม่เมื่อกระบวนการล้ม

หากอ่าน CSV จริงไม่ได้ Dashboard อาจแสดงข้อมูลตัวอย่างให้ผู้ดู Dashboard เห็น แต่ตัวเชื่อม Chatbot ตรวจค่า `source == remote_csv_live` และจะ **ไม่ใช้ข้อมูลตัวอย่างมาตอบว่าเครื่องว่าง** โดยจะบอกว่ายังยืนยันสถานะสดไม่ได้

## งานภาษาอังกฤษจากรีวิว 200 ข้อ

- ชุดคำถามอังกฤษ 200 ข้อมีอยู่แล้วและจับคู่กับคำถามไทยครบ 200 ข้อ จึงจัดทำ *คำตอบอ้างอิงอังกฤษฉบับรอตรวจ* โดยแปลเจตนาคำถามและข้อเสนอแนะผู้รีวิวไทย แยกคำตอบตาม 40 สถานการณ์ × 5 สำนวน เก็บใน `intent_trap_english_reference_200_20260926.jsonl` และสำเนาใหม่ใน `data/eval/` ของโปรเจกต์ ไม่ทับ Gold หรือไฟล์รีวิวเดิม
- ไฟล์รีวิวที่ตรวจได้มีคำตัดสินด้วยมือ 200 รายการ: ไทย 199, อังกฤษ 1; ข้อไทยที่เหลือใช้ข้อสรุปจากสำนวนพี่น้อง 4 ข้อและติดป้าย `thai_sibling_projections` ไว้ ไม่กล่าวว่า 200 คำตอบอังกฤษผ่านคนตรวจแล้ว
- 150 ข้อเกี่ยวกับสิทธิ์เข้าใช้ อาหาร และอุปกรณ์มีป้าย `pending_owner_policy_confirmation`; อีก 50 ข้อเกี่ยวกับขอบเขตการตอบมีป้าย `ready_for_human_semantic_review` ยังไม่เผยแพร่เป็นนโยบายที่เจ้าของรับรอง
- วิเคราะห์ความต่างของคำตอบเก่า: 31 คู่มี route/status ไทย–อังกฤษไม่ตรงกัน, 10 คำตอบอังกฤษให้ความช่วยเหลือน้อยกว่าไทย, 5 หมายเหตุไทยไม่ตอบเอกสาร ID ที่ถาม, 2 หมายเหตุอาหารพูดเรื่องจอง/จ่ายเงินนอกประเด็น

## การทดสอบและแก้เฉพาะจุด

- ทดสอบ current flow แบบ deterministic โดยปิด optional LLM/RAG fallback ครบ 200 ข้อก่อนและหลังแก้; 40 สถานการณ์ แต่ละสถานการณ์มี 5 สำนวน และคำตอบ/route ภายในแต่ละกลุ่มตรงกัน
- พบและแก้คำตอบอังกฤษ 3 สถานการณ์ × 5 สำนวน = **15 ข้อ**: ถามอากาศแล้วตอบว่าไม่มีข้อมูลอากาศพร้อมบอกขอบเขต, ถามเรื่องนอกขอบเขตแล้วบอกขอบเขต, และถามว่าไม่รู้จะถามอะไรแล้วแนะนำหัวข้อที่ระบบตอบได้ คำตอบอีก 185 ข้อไม่เปลี่ยน
- ชุด regression ที่เกี่ยวข้องผ่าน **50/50**; ZIP r3 มี **630 รายการ**, ตรวจความสมบูรณ์ผ่าน, hash ของไฟล์ภาษาอังกฤษตรงกับโปรเจกต์, และไม่มี log สนทนาภายใน ZIP
- ผลข้างต้นยืนยันการทำงานกับข้อความทดสอบและการส่งไฟล์เข้าแพ็กเกจ **ไม่ได้ยืนยัน** ความถูกต้องของสถานะจองจากรายการ WordPress จริง, ความครบถ้วนของภาษาอังกฤษทุกนโยบาย, หรือการเริ่มระบบบนเครื่องเจ้าของจริง
- ลองตรวจ health ของพอร์ต 8080 และ 8091 จากสภาพแวดล้อมงานนี้แล้วทั้งคู่หมดเวลาเชื่อมต่อ จึงไม่มีหลักฐานว่าบริการจริงบนเครื่องเจ้าของกำลังทำงานหรือไม่

## สิ่งที่ยังต้องตรวจด้วยข้อมูลจริง

1. ให้เจ้าของเลือก 3 กรณีจองจริงโดยบอกเพียง **วันที่, เวลา, ชื่อเครื่อง/ช่อง และผลที่เห็นในระบบจองว่า “ว่าง” หรือ “ไม่ว่าง”**: อย่างน้อยหนึ่งรายการจองสำเร็จ, หนึ่งรายการยกเลิกหรือไม่มา, และหนึ่งช่วงที่ควรว่าง ไม่ต้องส่งชื่อ เบอร์ หรืออีเมลผู้จอง จากนั้นเทียบข้อมูล WordPress → Dashboard API → คำตอบ Chatbot ทีละกรณี
   การดึง CSV สำเร็จยืนยันเพียงว่าเข้าถึงไฟล์ export ได้ ยังไม่ยืนยันว่า WordPress อัปเดตไฟล์ทันหลังการจอง/ยกเลิก จึงควรตรวจเวลาอัปเดตจริงในกรณีเหล่านี้ด้วย
2. ให้เจ้าของยืนยันคำตอบนโยบายเกี่ยวกับบุคคลภายนอก, การนำอาหาร/เครื่องดื่มเข้าไป, และอุปกรณ์ที่บุคคลภายนอกใช้ได้ ก่อนใช้ 150 คำตอบอังกฤษเป็นคำตอบอ้างอิงที่อนุมัติ
3. หากต้องการให้ตอบได้หลังเปิด Windows โดยไม่ต้องกด launcher ให้กำหนดวิธีเริ่มอัตโนมัติและเฝ้ากระบวนการบนเครื่องเจ้าของ ระบบในรอบนี้ทำได้เพียงเริ่มแบบเบื้องหลังด้วยตนเอง

แพ็กเกจ r3 สร้างในโฟลเดอร์ใหม่และเก็บ r2, ตารางเจ้าของ, ไฟล์ Git ที่ยังไม่บันทึก และ log เดิมไว้
